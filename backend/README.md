# MMWS Backend API (AMI/HES Core) — Этап 1: MVP чтения

FastAPI-сервис бизнес-логики (ТЗ п. 4.1): аутентификация/роли, реестр
`gateways`, справочник `meters`, асинхронные задачи чтения через
Protocol Gateway по gRPC, журнал аудита.

## Стек

PostgreSQL + SQLAlchemy 2.0 (async, asyncpg) + Alembic + FastAPI + JWT
(python-jose) + bcrypt (passlib) + Fernet-шифрование секретов счётчиков
(cryptography) — согласно `../Promt_MMWS.md`, раздел 2, и `../DECISIONS.md`.

## Запуск (Docker Compose — рекомендуется)

```bash
cd ..   # корень репозитория
cp backend/.env.example backend/.env   # заполнить секреты, права 600
docker compose up -d
```

Поднимает `postgres`, `gateway-risesun` (gRPC-обёртка Gateway из
Этапа 0) и `backend` (применяет миграции и бутстрапит первого
Супер-администратора автоматически при старте).

## Запуск локально (для разработки)

```bash
python3 -m pip install --user -r requirements.txt
python3 -m pip install --user -e ../gateway
cp .env.example .env   # заполнить секреты
python3 -m alembic upgrade head
python3 -m app.bootstrap                      # создаёт первого Супер-администратора
python3 -m mmws_gateway.grpc_server &          # отдельным процессом
python3 -m uvicorn app.main:app --reload
```

## Тесты

```bash
python3 -m pytest -q
```

Использует отдельную БД `mmws_test` (создать один раз:
`docker compose exec postgres psql -U mmws -c "CREATE DATABASE mmws_test;"`),
схема пересоздаётся на каждый тестовый прогон (`tests/conftest.py`).
Тесты не поднимают воркер задач/gRPC — проверяют синхронные эндпоинты
(auth, RBAC, регистрация gateway, справочник счётчиков). Полный цикл
(задача → gRPC → Gateway → эмулятор счётчика → сохранённое показание)
проверен вручную сквозным прогоном при разработке; отдельный
автоматизированный e2e-тест с реальным gRPC-вызовом — кандидат на
следующую итерацию.

## Архитектурные решения этого этапа

- **Роли** (ТЗ п. 4.2.1) — не линейная иерархия: «Наблюдатель» видит
  данные, но не может запускать чтение, поэтому права заданы явными
  наборами по роли (`app/core/permissions.py`), а не сравнением уровней.
- **Асинхронные задачи** (ТЗ п. 4.7, Promt_MMWS.md принцип 3) —
  персистентная очередь в PostgreSQL (таблица `jobs`), не in-memory;
  воркер — `SELECT ... FOR UPDATE SKIP LOCKED` внутри процесса Backend
  (совместимо с несколькими экземплярами Backend без дублирования
  обработки одной задачи); вынесение в отдельный процесс — естественное
  развитие для реальной горизонтальной нагрузки, не требуется для MVP.
- **Секреты счётчиков** — Fernet-шифрование в покое, расшифровка только
  на время вызова Gateway (`job_worker.py`); никогда не возвращаются
  через API (проверено тестом `test_meter_password_never_returned_*`).
- **Регистрация Gateway** — только через API с явным подтверждением
  ролью «Супер-администратор» (`POST /api/gateways` → `pending`,
  `POST /api/gateways/{id}/approve` → `approved`); счётчик нельзя
  привязать к неподтверждённому Gateway.
- **Бутстрап первого пользователя** (`app/bootstrap.py`) — иначе
  регистрация Gateway и управление пользователями (обе операции требуют
  существующего Супер-администратора/Администратора) невозможны при
  первом запуске системы. Идемпотентен, отключается после первого
  успешного создания.

## Не реализовано на этом этапе (последующие этапы ТЗ)

Запись параметров (Этап 2), профиль нагрузки/докачка (Этап 3),
расписания/схемы параметров (Этап 4), биллинг-интеграция и
Disconnect Control (Этап 5). Таблицы `parameter_write_history`,
`parameter_schemes`, `scheduled_jobs` не заведены — появятся вместе с
соответствующим функционалом, чтобы не плодить пустые таблицы заранее.
