# MMWS Frontend — Этап 1: минимальный веб-интерфейс

React + TypeScript SPA (Vite): вход, список счётчиков, карточка
счётчика с показаниями и журналами. Без функций записи —
Promt_MMWS.md, Этап 1: «Минимальный Frontend: список счётчиков,
карточка счётчика, просмотр показаний/журналов. Без функций записи.»

## Запуск

Node.js на сервере разработки нет (см. `../DECISIONS.md`) — сборка и
установка зависимостей идут только через Docker.

```bash
cd ..   # корень репозитория
docker compose up -d frontend   # соберёт и поднимет nginx на :5173, проксирующий /api на backend
```

Для локальной разработки с горячей перезагрузкой:

```bash
docker run --rm -v "$(pwd)/frontend:/app" -w /app -p 5173:5173 \
  -e VITE_API_PROXY_TARGET=http://host.docker.internal:8000 \
  node:20-alpine sh -c "npm install && npm run dev"
```

## ⚠️ Ограничение проверки (2026-08-18)

Визуальная проверка в реальном браузере **не выполнена**. В этом
окружении нет GUI, а headless Chromium (Playwright) требует системных
библиотек (`libatk`, `libnss3` и др.), для установки которых нужен
интерактивный пароль `sudo` — недоступен ни агенту, ни через `!`
(sudo требует TTY). Что проверено вместо этого:

- `npm run build` (TypeScript-компиляция + Vite-сборка) проходит без
  ошибок в Docker.
- Production-образ (nginx + собранный бандл) поднимается и отдаёт
  `index.html`; прокси `/api/*` на `backend` в docker-сети проверен
  curl'ом (неверный логин корректно возвращает 401 с ожидаемым телом).
- Код (роутинг, редиректы после входа/выхода, обработка ошибок API)
  вычитан вручную на предмет логических ошибок.

**Не проверено**: реальный рендеринг DOM, взаимодействие пользователя
(клики, ввод форм), WebSocket-обновление статуса задачи в браузере.
Первая же реальная проверка в браузере (в том числе на устройстве
человека) — обязательный шаг перед тем, как считать Этап 1 закрытым.

## Архитектурные решения

- **Хранение токенов** — `localStorage` (не httpOnly cookie): backend
  возвращает токены в теле JSON-ответа, а не через `Set-Cookie`.
  Приемлемо для MVP при условии, что вывод в React экранируется по
  умолчанию (ТЗ п. 4.5, защита от XSS) и нигде не используется
  `dangerouslySetInnerHTML`.
- **RBAC на фронтенде — только UX**, не источник правды: кнопка
  «Обновить показания» скрывается для ролей без `trigger_read`
  (`auth/AuthContext.tsx:canTriggerRead`), но реальная проверка прав
  всегда выполняется на Backend (роль читается из JWT-payload без
  проверки подписи — сделать что-то запрещённое через подделку роли в
  токене на клиенте всё равно не даст, подпись проверяется на сервере).
- **WebSocket для статуса задачи чтения** (ТЗ п. 4.2.12) — токен
  передаётся query-параметром (`?token=`), т.к. браузер не позволяет
  задать заголовок `Authorization` при установлении WS-соединения.
