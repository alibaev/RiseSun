# Решения по стеку и инфраструктуре

## Язык Protocol Gateway: Python (не Node.js)

`Promt_MMWS.md`, раздел 2, фиксирует выбор: «Node.js (TypeScript) либо
Python — выбрать один и придерживаться». Это явно допустимая альтернатива,
а не отклонение от согласованного стека, поэтому не требует остановки
работы и подтверждения (в отличие от отклонения от самого перечня
технологий).

Причина выбора Python, а не Node.js:

- На сервере разработки (`~/mmws`) отсутствует Node.js/npm, а системный
  `apt install` требует пароль sudo, недоступный агенту в автономном режиме.
- Python 3.10 уже присутствует в системе и достаточен для реализации
  бинарных протоколов (`socket`, `struct`, `asyncio`) без сторонних
  зависимостей, кроме `pytest` для тестов (установлен через `pip install
  --user`, без sudo).

Следствие для следующих этапов (см. `Promt_MMWS.md`, раздел 2, сноска
«должен совпадать по языку с Gateway»): Backend API на Этапе 1 должен быть
на **FastAPI**, а не NestJS, чтобы не плодить два рантайма.

Если к моменту Этапа 1 на сервере будет доступен Node.js и человек явно
захочет TypeScript — потребуется пересмотреть это решение до начала
Этапа 1, так как гайдлайн прямо запрещает менять стек внутри уже начатой
работы без согласования.

## Проверка на реальном оборудовании (2026-08-18): расхождения с ТЗ

При первой попытке прочитать показания с реального счётчика Risesun
(серийный номер `202001002352`, подключение через сервер по адресу
`192.168.144.73:2009`) обнаружены два расхождения с зафиксированным ТЗ.
Оба подтверждены человеком (владельцем проекта) как фактическое поведение
реального оборудования, а не ошибка настройки или временная неполадка.

### 1. Модель TCP-соединения — счётчик инициирует, а не Gateway

ТЗ, раздел 4.3.1 (Table 1): «Gateway инициирует TCP-соединение к
IP-адресу и порту счётчика, указанным в справочнике». По факту этот
конкретный счётчик работает в режиме «звонок домой» (типично для
GPRS-счётчиков без статического IP/за NAT оператора): счётчик сам
устанавливает исходящее TCP-соединение на IP:порт сервера Gateway.
Текущий транспортный слой (`transport.py`, класс `TcpTransport`)
реализует только клиентский режим (Gateway — инициатор) и не умеет
слушать входящие соединения.

Следствие: транспортный слой Gateway должен поддерживать оба режима
— исходящее подключение (для счётчиков со статическим IP/Ethernet,
как в ТЗ) и приём входящего соединения со сопоставлением по серийному
номеру, который счётчик сообщает о себе при подключении (см. п. 2
ниже). Это архитектурная доработка, выходящая за рамки PoC Этапа 0 —
запланировать отдельной задачей до/в рамках Этапа 1, реализация ещё не
начата (см. TODO ниже).

### 2. Протокол — DL/T645-2007, а не IEC 62056-21 / HDLC-DLMS

ТЗ, раздел 4.3.2, фиксирует ровно три протокольных профиля для
счётчиков Risesun: IEC 62056-21 режим C, режим E, HDLC + DLMS/COSEM.
Ни OBIS.xlsx, ни API.docx протокол DL/T645 не упоминают — это не
рассматривавшийся в проекте протокол.

По факту счётчик `202001002352`, подключившись, без запроса с нашей
стороны сразу присылает кадр китайского национального протокола
**DL/T 645-2007**:

```
68 13 41 00 06 23 20 68 15 0e 46 74 33 39 56 53 56 34 2e 30 31 38 39 39 22 16
```

Разбор: `68` старт · `13 41 00 06 23 20` адрес счётчика (6 байт BCD) ·
`68` повторный старт (канонично для DL/T645) · `15` код управления ·
`0e` длина данных (14) · 14 байт данных (после стандартного для
DL/T645 сдвига `+0x33` на байт расшифровываются как `13 41 00 06 23 20
23 01 fb fd fe 05 06 06` — первые 6 байт повторяют адрес, типичное
поведение login/heartbeat-кадра) · `22` контрольная сумма · `16` стоп-байт
(тоже канонический для DL/T645). Ни один из трёх профилей ТЗ такого
кадра не порождает — весь код Этапа 0 (`protocols/mode_c.py`,
`mode_e.py`, `hdlc_dlms.py`) рассчитан на DLMS-семейство и для DL/T645
не подходит ни по кадрированию, ни по адресации, ни по системе команд.

Человек (владелец проекта) подтвердил: у этого счётчика реально
поддерживается только DL/T645, переключение на DLMS/HDLC не
рассматривается.

**Статус: подтверждённое расхождение с ТЗ, требует формального решения
о расширении раздела 4.3.2 (либо допсоглашения), т.к. добавляет
четвёртый протокольный профиль вне первоначально описанного объёма
Этапа 0.**

#### Ход попыток чтения (2026-08-18) и текущий блокер

Подтверждено на реальном оборудовании (два счётчика подключались на
`192.168.144.73:2009`, второй с адресом `52 23 00 01 20 20`, помимо
первого `13 41 00 06 23 20` = серийный `202001002352`):

- Конверт кадра и алгоритм контрольной суммы (сумма байт от первого
  `0x68` до конца данных, mod 256; данные — со сдвигом `+0x33` на
  байт) — подтверждены дважды на реальных login-кадрах, которые оба
  счётчика присылают сами сразу после установления TCP-соединения
  (`control=0x15`, эти 14 байт данных — исходно оказываются копией
  6-байтного адреса плюс ещё 8 байт, судя по всему часть служебной
  информации login-кадра, не разобрана).
- Попытка №1 — DL/T645-2007: `control=0x11` (читать данные), DI
  (4 байта) = `00 00 00 00` (общестандартный код «активная энергия
  суммарно») — **ответа нет**.
- Попытка №2 — низкоуверенное приближение DL/T645-1997: `control=0x01`
  (читать данные), DI (2 байта) = `00 00` — **ответа нет**.
- Важное замечание по безопасности на будущее: код `0x11` в редакции
  1997 года означает не «чтение», а «изменение пароля» — при
  дальнейших экспериментах с control-кодами использовать только
  заведомо безопасные (чтение), не трогать write/config-коды без
  железного подтверждения их семантики.

**Блокер:** ни один код показателя не подошёл (тишина в обоих случаях,
не отказ — значит, либо код показателя не тот, либо перед чтением
требуется какой-то ответный кадр/подтверждение на login от нас, либо
это вообще проприетарный протокол Risesun поверх DL/T645-совместимого
конверта). Дальнейший подбор вслепую на реальном (возможно, уже
включённом в боевой контур) оборудовании признан нецелесообразным без
дополнительной информации.

**Рекомендованный следующий шаг (не выполнен, ждёт решения человека):**
получить от Risesun официальную протокольную документацию под этот
конверт кадра, либо снять трафик существующего десктоп-приложения
Risesun Smart Meter Manage v2.0.1.5 (упомянуто в `Promt_MMWS.md`,
раздел 1) при его штатной работе с этими счётчиками — это даст
эталонный пример реально работающего запроса/ответа вместо подбора.

#### Прорыв (2026-08-18): текстовые логи legacy-приложения расшифрованы

Человек скопировал с Windows-машины, где реально работает Risesun
Smart Meter Manage, текстовые протокольные логи операции «прочитать
показания» для обоих счётчиков (`202001002352.txt`,
`202306004113.txt` — 20 строк каждый, метка времени + hex-кадр).
Разобраны полностью через существующий код Gateway (`hdlc.py`,
`dlms.py`, `datatypes.py`) с ручным патчем многобайтной HDLC-адресации
(в PoC она не реализована) — все HCS/FCS контрольные суммы сошлись,
структура полностью подтверждена. **Это НЕ DL/T645** — приложение
использует ровно профиль ТЗ «HDLC + DLMS/COSEM» (SNRM/UA → AARQ/AARE →
GET.request/GET.response), но с деталями, которых сейчас нет в PoC:

1. **HDLC-адрес счётчика — 4 байта**, не 1: `(upper=1,
   lower=<последние 5 цифр серийного, как целое число>)`. Для
   `202001002352` → `lower=2352`. Кодировка: upper и lower каждый — 2
   байта, старший байт первым, внутри байта `(значение << 1) | 1` для
   последнего байта подполя, `(значение << 1)` для небольшого. Текущий
   `_encode_hdlc_address`/`_decode_hdlc_address` в `hdlc.py`
   поддерживают только однобайтную адресацию (0..127) — нужно
   расширять.
2. **Адрес клиента (Gateway) = `0x30` (48)**, а не
   `DEFAULT_CLIENT_ADDRESS = 0x10`, как сейчас в коде.
3. **Информационное поле I-кадра обёрнуто в 3-байтный LLC-заголовок**:
   `E6 E6 00` для кадров от клиента, `E6 E7 00` для кадров от
   счётчика — перед собственно AARQ/AARE/GET-тегами. Сейчас в
   `dlms.py` это не учтено, разбор/сборка кадров идёт без LLC-обёртки.
4. **AARQ реального счётчика содержит больше полей**, чем строит
   `build_aarq`: `sender-acse-requirements` (тег `0x8A`),
   `mechanism-name` (тег `0x8B`, OID low-level-security `{2 16 756 5 8
   2 1}`), и `user-information` (тег `0xBE`) с обёрнутым xDLMS
   Initiate Request (тег `0x01` с proposed-dlms-version,
   proposed-conformance, client-max-receive-pdu-size). Без этих полей
   ассоциация с реальным счётчиком, вероятно, не установится —
   `build_aarq`/`parse_aarq` нужно расширять.
5. **Пароль передаётся как есть** (`calling-authentication-value`,
   теги `0xAC`→`0x80`→байты пароля ASCII) — та часть, что уже
   реализована, совпадает с реальным трафиком.
6. **Фактическое значение параметра — не по стандартному OBIS
   `1.8.0`, а по вендорскому `96.80.0`** (подтверждено словарём
   `OBIS.xlsx`, лист `Read_Tree_полное_дерево`: `96.80.0` подписан
   «Total» именно под веткой «Total Active Energy»). Приложение сначала
   GET'ит `scaler_unit` (атрибут 3) для `1.8.0` и `31.7.0`
   (Instantaneous Current), затем **value** (атрибут 2) для `96.80.0`
   — т.е. коды для метаданных и для самого значения у Risesun разные,
   и оба нужны из словаря OBIS, не из общих стандартов DLMS.
7. **Формат числа значения отличается по счётчику**: у
   `202001002352` — тег `0x05` (double-long/int32, 4 байта); у
   `202306004113` — тег `0x14` (long64/int64, 8 байт). `datatypes.py`
   сейчас не поддерживает ни `0x14`, ни структуры (`0x02`, нужны для
   scaler_unit), ни enum (`0x16`, нужен для unit) — все три придётся
   добавить.
8. Расчёт по найденным данным (scaler=1, unit=30/Wh, raw×10^scaler):
   `202001002352` → **666.19 кВт·ч**, `202306004113` → **4506.75
   кВт·ч** — правдоподобные показания, разбор признан достоверным.

**Открытый вопрос на момент первого pcap (решён следующим дампом, см.
ниже):** человек подтвердил, что оба счётчика подключаются к серверу
на `192.168.144.73:2009`/`192.168.144.79:2009` и в login-кадре
сообщают некие свои данные. В первых двух pcap-дампах (см. выше) не

#### Полный дамп с TCP SYN (`n202306004113.pcapng`) — разгадка

Получен второй заход дампа с Windows-машины, на этот раз захватывающий
сессию с самого TCP SYN. Полная последовательность для счётчика
`202306004113` (порт-адрес закреплялся не с первой попытки — счётчик
открыл и сразу же оборвал (RST) два неудачных соединения подряд, `56039`
и `56040`, прежде чем `56041` осталось активным — видимо, внутренняя
логика реконнекта самого счётчика, не наша забота):

1. `t=354.155` — счётчик, независимо от нас, шлёт login-кадр (DL/T645-конверт,
   те же 26 байт, что и раньше).
2. `t=354.156` — **приложение отвечает `00 00 00` (3 байта)** — но это
   НЕ ack именно на login: тот же самый обмен `счётчик 6 нулевых байт
   → сервер 3 нулевых байта` повторяется независимо каждые ~60 секунд
   на протяжении всей сессии (видно в дампе на t≈473, 534, 595, 656) —
   это отдельный keepalive-пинг/понг, никак не привязанный к
   логин-кадру.
3. **`t=400.839` — только тут приложение впервые шлёт SNRM** — разрыв
   **~46 секунд** между login-кадром счётчика и первым байтом от
   приложения. Это чисто человеческая задержка (оператор кликнул
   «прочитать показания» не сразу) — счётчик, судя по всему, готов
   ждать сколь угодно долго и **не требует никакого подтверждения на
   свой login-кадр**. Держать соединение открытым (не рвать) и отвечать
   на периодические keepalive-пинги — этого достаточно.

**Вывод: наша гипотеза про обязательный ack на login была неверной.**
Единственная реальная причина, по которой прямые живые попытки этой
сессии (см. ниже) не сработали — что мы отправляли SNRM буквально
сразу (миллисекунды) после вычитывания login-кадра, без какой-либо
паузы. Пробуем добавить паузу перед SNRM как рабочую гипотезу №2.

#### Перенос находок в рабочий код Gateway (2026-08-18, тот же день)

По решению человека («сначала доработать Gateway под реальное железо,
потом Этап 1») все находки этой сессии перенесены из
scratch-скриптов в `gateway/src/mmws_gateway`:

- `protocols/hdlc.py`: многобайтная (1/2/4 байта) адресация
  (`server_hdlc_address`, обобщённые `_encode_hdlc_address`/
  `_decode_hdlc_address`), `DEFAULT_CLIENT_ADDRESS=0x30`,
  `SNRM_PARAMETER_NEGOTIATION`. Известное новое ограничение:
  физический адрес (последние 5 цифр серийного) должен умещаться в 14
  бит (≤16383) — значения 16384..99999 пока не поддержаны
  (`server_hdlc_address` бросает `ValueError`).
- `protocols/dlms.py`: LLC-обёртка (`wrap_llc_command`/
  `wrap_llc_response`/`unwrap_llc`), расширенный `build_aarq`
  (sender-acse-requirements, mechanism-name LLS, user-information/
  InitiateRequest), `parse_aare` переписан на генерический TLV-скан,
  `build_get_request` получил параметр `attribute_id` (нужен для
  чтения `scaler_unit`, атрибут 3, отдельно от `value`, атрибут 2).
- `protocols/datatypes.py`: добавлены `structure`(0x02), `array`(0x01),
  `enum`(0x16), `long64`/`long64-unsigned`(0x14/0x15).
- `transport.py`: `TcpServerTransport.from_accepted_socket` — базовый
  строительный блок для серверного (call-home) транспорта; полноценный
  листенер с реестром/keepalive пока не реализован.
- `emulators/hdlc_dlms_emulator.py`: обновлён под LLC-обёртку, чтобы
  интеграционные тесты остались согласованы с реальным форматом.
- Новый тест `tests/test_real_capture_replay.py`: побайтовая сверка
  нашего `encode()` (SNRM/AARQ/GET) с реальным трафиком и корректный
  `decode()` реальных ответов счётчика, включая вычисление показания
  666.19 кВт·ч из сырых байт GET.response — сильнее эмулятора, т.к.
  эталон здесь — байты настоящего рабочего клиента.
- `gateway/README.md`: статус DoD и список открытых инженерных решений
  обновлены — большинство пунктов, помеченных как «требует проверки на
  реальном оборудовании», закрыты; транспортная модель «звонок домой»
  и точный тайминг SNRM после логина остаются открытыми.

Результат: **75 тестов, все зелёные** (было 65). Живое чтение с
реального звонящего домой счётчика через CLI/Gateway всё ещё не

## Найден и исправлен протокольный баг при проверке кнопки «Обновить показания» (2026-08-18)

Человек попросил проверить кнопку «Обновить показания» вживую. Для
этого поднят программный эмулятор счётчика в docker-сети
(`meter-emulator:4059`, тот же образ Gateway) и создан тестовый счётчик
через API. Первые попытки чтения падали нестабильно: иногда проходили,
иногда — `ConnectionResetError` где-то в середине протокольного обмена.

**Найдена настоящая причина** (не сетевая — протокольная): для
серийного номера `999000111222` второй байт HCS (CRC16 заголовка
HDLC-кадра) GET.request случайно совпадает по значению с открывающим/
закрывающим флагом HDLC (`0x7E`). Чтение кадра в `read_frame_from_transport`
(`protocols/hdlc.py`) и в эмуляторе (`_read_frame`,
`emulators/hdlc_dlms_emulator.py`) было реализовано через сканирование
байт до первого `0x7E` (`recv_until`) — при таком совпадении кадр
обрезался раньше времени, что и давало разрыв соединения при чтении
ответа. Настоящий HDLC устраняет это байт-стаффингом на битовом уровне
физического канала; PoC этого не реализовывал с самого Этапа 0, но
баг не проявлялся, пока адресация была однобайтной (меньше
вариативности CRC-байт) — переход на 4-байтную адресацию (см. выше)
сделал совпадение регулярным, а не гипотетическим.

**Исправление:** оба места чтения кадра переписаны на чтение строго по
объявленной длине из поля Frame Format (2 байта сразу после
открывающего флага), а не сканированием до следующего `0x7E` — корректно
и безопасно, поскольку TCP уже гарантирует надёжную доставку байт и
настоящий байт-стаффинг избыточен поверх него. Добавлены регрессионные
тесты с этим же серийным номером (`999000111222`, детерминированно
провоцирует баг) — на уровне сборки/разбора кадра и сквозной через
эмулятор. 77 тестов Gateway, все зелёные (было 75). Проверено вживую
через полный путь API → задача → gRPC → эмулятор: 3/3 успешных чтения
подряд после исправления (до — падало стабильно).

**Подтверждено человеком вживую в браузере**: кнопка «Обновить
показания» на карточке счётчика `999000111222` отработала, показание
`1234567` отобразилось. Первая полностью живая, ручная, сквозная
проверка UI-действия (клик → задача → gRPC → Gateway → счётчик →
показание в интерфейсе), а не только через curl/API.

## Живое чтение с реального счётчика — успех (2026-08-18)

Закрыт последний открытый вопрос по протокольному слою Этапа 0/1
(«живое чтение с реального звонящего домой счётчика ещё не
подтверждено», см. выше).

### Модель поведения счётчика (по информации от человека, подтверждено практикой)

Счётчик держит до **10 одновременных кандидатных TCP-соединений** к
серверу; при попытке открыть 11-е — сервер должен закрывать САМОЕ
СТАРОЕ из уже открытых (скользящее окно, а не «принять 10 и
остановиться»). Счётчик перестаёт открывать новые соединения, как
только НА ОДНОМ из держащихся реально начинается протокольный обмен
(сервер отвечает валидным HDLC). Реализовано в
`live_read_sliding_window.py` (scratchpad): при 11-м соединении
вытесняется 1-е по времени; на каждом держащемся соединении сервер
**повторно** посылает SNRM каждые 4с (не один раз и не после паузы -
раньше пробовали и то, и другое по отдельности, не сработало), пока
соединение не даст успех либо не будет вытеснено.

### Результат

Соединение #1 (счётчик `202306004113`) ответило на **4-й попытке**
SNRM (~16с повторов на одном и том же соединении, без необходимости
вытеснения — второй счётчик в этот раз не звонил). Прочитано значение
вендорского OBIS `96.80.0` (см. выше про несовпадение с ТЗ-стандартным
`1.8.0`): `450701` (сырое). С учётом scaler=1/unit=30(Wh), найденных
ранее по этому же счётчику: **4507.01 кВт·ч** — совпадает по порядку
величины с более ранним значением из pcap-анализа того же дня
(4506.75 кВт·ч), с учётом естественного роста показания за прошедшее
время. Это первое настоящее живое чтение с реального оборудования
через собственный код Gateway (не воспроизведение байт из pcap, не
эмулятор) — SNRM/AARQ/GET-запросы собраны обычным
`hdlc_dlms.read_register()` уже исправленного пакета.

### Что ещё предстоит формализовать (не сделано, живёт пока только в scratchpad-скрипте)

Логика скользящего окна из 10 соединений с вытеснением и повторными
SNRM — пока экспериментальный scratchpad-скрипт
(`live_read_sliding_window.py`), не перенесена в постоянный код
Gateway (`transport.py`/`grpc_server.py`). Перенос — отдельная задача:
нужно решить архитектурно, как этот call-home листенер с пулом
соединений сочетается с моделью «один gRPC-вызов = одно чтение»
(`ReadRegister`) и с реестром `meters`/`gateways` в Backend (сейчас
адрес счётчика в БД — `ip_address`/`port`, подразумевающие исходящее
подключение Gateway к счётчику, а не наоборот). Не блокирует Этап 1
(уже закрыт), но обязательно к решению до того, как реальные звонящие
домой счётчики будут работать через полный путь Backend → gRPC →
Gateway → счётчик, а не только через ручной scratchpad-скрипт.

## Перенос логики скользящего окна в постоянный код (2026-08-18)

По прямому указанию человека («перенеси логику скользящего окна в
постоянный код») scratch-скрипт `live_read_sliding_window.py`
формализован в `gateway/src/mmws_gateway/callhome.py`:

- `serial_from_dlt645_address()` — обобщённая реконструкция серийного
  номера из адреса login-кадра (реверс порядка байт, BCD), без
  заранее заданного справочника — работает для ЛЮБОГО серийного
  номера, не только двух проверенных.
- `CallHomePool` — слушает call-home порт, держит скользящее окно из
  `window_size` (по умолчанию 10) соединений, вытесняя самое старое
  при переполнении; фоново опознаёт каждое по login-кадру.
- `read_via_call_home()` — забирает held-соединение для нужного
  серийного номера и повторяет SNRM+полный обмен с интервалом, пока
  один не даст успех либо не истечёт таймаут.
- `proto/gateway.proto`: добавлено поле `bool call_home` в
  `ReadRegisterRequest`; `grpc_server.py` при `call_home=true`
  делегирует в `read_via_call_home()` вместо набора `host:port`.

### Серьёзный баг найден и исправлен при переносе (важно для будущих похожих фильтров)

Первая версия `DlT645FilteringSocket` фильтровала байт `0x00`
("одиночный keepalive-пинг") **везде в потоке**, не только на границе
между кадрами. Это ломало настоящие HDLC-кадры, у которых `0x00`
законно встречается ВНУТРИ содержимого (например, в 4-байтном адресном
поле UA-ответа: `...61 00 02 24 61...`) — фильтр съедал такие байты,
как будто это шум, и кадр приходил обрезанным/сдвинутым. В тестах это
проявлялось как «счётчик как будто снова прислал SNRM вместо AARQ» —
разгадка заняла несколько итераций (сравнение живого ручного прогона,
который случайно не задевал `0x00` в нужном месте, с детерминированно
падающим pytest-тестом, который его задевал).

**Исправление:** фильтрация переведена в явный двухфазный режим —
активна только пока идёт поиск НАЧАЛА следующего кадра (`_seeking`);
как только найден первый настоящий байт кадра, все последующие байты
ЭТОГО кадра отдаются без фильтрации; режим поиска включается заново
явным вызовом `reset_seeking()` перед каждой новой попыткой SNRM.
Регрессионный тест `test_read_via_call_home_succeeds_after_ignored_snrm_attempts`
воспроизводит ровно этот сценарий (эмулированный счётчик, отвечающий
только на 3-ю попытку SNRM, с реальным UA-кадром, содержащим `0x00`
внутри). 83 теста Gateway, все зелёные (было 77).

### Не сделано в этом переносе (следующий шаг)

Backend пока не умеет ЗАПРАШИВАТЬ call-home чтение: в схеме `meters`
нет поля «этот счётчик call-home», `job_worker.py`/`gateway_client.py`
всегда шлют `call_home=false` и адрес `ip_address:port` для исходящего
подключения. Чтобы реальные звонящие домой счётчики заработали через
полный путь Backend → gRPC → Gateway (а не только через ручной вызов
`read_via_call_home()` напрямую), нужно: добавить поле
транспортного режима в `Meter` (миграция), прокинуть `call_home=true`
из `job_worker.py` при чтении таких счётчиков, и поднять call-home
пул в `docker-compose.yml` (порт 2009 наружу у сервиса `gateway-risesun`,
аналогично тому, как уже открыт `5173` у `frontend`).

## Backend-интеграция call-home: код готов, живая проверка вскрыла нестабильность реального устройства (2026-08-18)

Сделано и протестировано (109 тестов, gateway 83 + backend 26, все
зелёные): `Meter.is_call_home` (миграция `16cf39318ca9`, nullable
`ip_address`/`port`), валидация в схемах (`MeterCreate` требует
`ip_address`/`port` ТОЛЬКО если не call-home), `job_worker.py`
прокидывает `call_home`/увеличенный `call_timeout_s` в
`read_register()`, порт 2009 открыт наружу в `docker-compose.yml`.
`DELETE /api/meters/{id}` с историей корректно отдаёт 409 вместо 500
(отдельная регрессия, найденная и исправленная в этом же заходе).

Дальше пошла многочасовая живая проверка на реальном счётчике
202306004113 через полный путь Backend → gRPC → Gateway, которая
вскрыла, что call-home транспорт устроен сложнее, чем казалось после
первого единичного успешного чтения (см. секцию про скользящее окно
выше):

1. **Held-соединение без единой попытки SNRM за ~60с становится
   полностью неработоспособным** — не отвечает вообще ни на что, хотя
   TCP-сокет технически не закрыт. Экспериментально подтверждено
   дважды (60с и отдельно ~120с простоя). Фикс: `CallHomePool.claim()`
   принимает `max_age_s` и отказывается отдавать held-соединения
   старше `DEFAULT_MAX_CLAIM_AGE_S` (30с) — вызывающий код просто ждёт
   следующее свежее вместо того, чтобы биться в заведомо мёртвое.
2. **Задержка ответа устройства (UA на SNRM, AARE на AARQ,
   GET-response) крайне нестабильна** — наблюдались варианты от ~3 до
   ~19+ секунд без чёткой закономерности, даже на гарантированно свежих
   (только что принятых) соединениях. Испробованы и не дали устойчивого
   успеха: короткий таймаут на попытку (3с) + частые повторы; длинный
   единственный таймаут (12-15с) без повтора на этом же соединении;
   таймаут, настроенный так, чтобы не резонировать с наблюдаемым ~7с
   циклом (9с таймаут + минимальная пауза 0.5с). Во всех вариантах
   ответ систематически приходил ЧУТЬ ПОЗЖЕ, чем истекал текущий
   таймаут — то есть либо реальная задержка ответа сама плывёт вместе с
   любым выбранным таймаутом (что подозрительно и может означать, что
   устройство как-то реагирует на сам факт повторной отправки SNRM,
   сбрасывая свой внутренний отсчёт), либо это просто очень высокая
   сетевая/аппаратная джиттер-задержка без какой-либо связи с нашим
   поведением. Причина не выяснена окончательно.
3. Промежуточная попытка — заранее (в фоне) прогревать SNRM/UA сразу
   при опознании соединения, отдельно от момента реального запроса
   чтения — не решила проблему: если между прогревом и AARQ проходит
   больше ~минуты, DLMS-ассоциация тоже "остывает" (счётчик отвечает
   RR-подтверждением на HDLC-уровне, но не даёт настоящего AARE) — то
   есть разносить SNRM и AARQ по времени тоже не работает, они должны
   идти одним непрерывным заходом (что и реализовано в текущем коде).

**Текущее состояние**: код архитектурно корректен и покрыт тестами
(включая добавленный при диагностике пропуск S-кадров/RR-подтверждений
в `_recv_i_frame`, которых реальное устройство шлёт больше, чем
ожидалось), но ни одна живая попытка чтения в течение этой сессии
(после первоначального единичного успеха, см. выше) не завершилась
успехом — все упирались в TIMEOUT на разных стадиях. Первоначальный
единичный успех был получен РУЧНЫМ scratch-скриптом, а не через
постоянный код, и его точные условия (тайминг, скрипт) не сохранены
буквально — поэтому неизвестно, отличался ли он чем-то существенным от
опробованных вариантов постоянного кода, кроме простого совпадения по
времени. Требуется либо дальнейшая диагностика с захватом трафика на
уровне TCP (Wireshark/tcpdump на стороне Gateway) для точного измерения
задержки СО СТОРОНЫ СЕТИ (отличить сетевой джиттер от поведения
устройства), либо принять текущий риск как известное эксплуатационное
ограничение call-home транспорта для этой модели счётчика.

## Захват трафика tcpdump: найдена настоящая первопричина — потеря пакетов на уровне TCP-хендшейка (2026-08-18)

Поднят `tcpdump` (в контейнере `--net=host`, снаружи Docker NAT, то
есть прямо на интерфейсе хоста) на порту 2009 во время очередной живой
попытки чтения. Результат оказался решающим: **почти все новые попытки
счётчика открыть TCP-соединение к Gateway НЕ ЗАВЕРШАЮТ трёхстороннее
TCP-подтверждение вообще.** В захваченном трафике видно (порты
63143-63146 счётчика в течение ~2 минут одной сессии):

```
meter SYN -> Gateway SYN-ACK (ответ мгновенный, микросекунды — Gateway не тормозит)
... нет ACK от счётчика ...
Gateway ретрансмиссия SYN-ACK (свой TCP RTO, экспоненциальный backoff)
... снова нет ACK ...
meter повторяет SYN (свой TCP RTO)
Gateway снова отвечает SYN-ACK
... цикл повторяется 5-10 раз для одного и того же порта, иногда безуспешно вообще
```

Это классический паттерн ПОТЕРИ ПАКЕТОВ на сетевом пути (обычно
IP SYN-ACK от Gateway до счётчика не доходит, либо ACK от счётчика не
доходит обратно до Gateway) — типично для нестабильного
GPRS/сотового канала или проблем NAT на промежуточном оборудовании.
Важно: raw-сокет Gateway (`accept()`) физически не может сработать для
такого наполовину открытого соединения — то есть подавляющее
большинство ПОПЫТОК счётчика подключиться Gateway вообще не видит на
уровне приложения; в лог попадают только те немногие соединения, что
случайно "прорвались" через эту потерю пакетов и полностью установили
TCP-сессию.

**Переоценка предыдущих находок**: это меняет интерпретацию всей
предыдущей многочасовой диагностики таймингов SNRM/UA/AARE. Скорее
всего наблюдавшаяся "нестабильная задержка ответа устройства
(3-19+ секунд)" объяснялась ТОЙ ЖЕ потерей пакетов — retransmit самих
данных (не только SYN) на том же лоссовом канале, а не особым
поведением прошивки счётчика. Гипотезы про "резонанс тайминга",
"остывание DLMS-ассоциации", "окно жизни соединения ~30-60с" были
построены на наблюдениях, искажённых этой сетевой потерей, и не
являются причиной сами по себе — они лишь следствие. Настоящая
первопричина — качество сетевого канала до реального счётчика, что
находится ВНЕ зоны ответственности кода Gateway/Backend.

**Вывод (первая версия, ниже уточнена)**: код (HDLC/DLMS-протокол,
call-home пул, повторные попытки) корректен и не требует дальнейшей
подгонки таймаутов — проблема на уровне сети/канала связи до
конкретного физического счётчика.

## Побайтовый разбор трафика и точечный тест: AARQ доставляется и подтверждается, но AARE не приходит даже за 45с (2026-08-18)

Пользователь спросил, не может ли счётчик отправлять части одного
ответа через РАЗНЫЕ из своих 10 held-соединений — гипотеза оказалась
неверна (весь обмен в захваченной сессии шёл на одном и том же TCP-
соединении от начала до конца), но проверка привела к куда более
точному диагнозу через побайтовый разбор hex-дампа пакетов:

1. SNRM (35 байт) и ответный UA (35 байт) побайтово совпадают с
   ожидаемыми константами кода (`SNRM_PARAMETER_NEGOTIATION`,
   `CONTROL_SNRM=0x93`, `CONTROL_UA=0x73`) — протокол/адресация/LLC
   реализованы верно, это подтверждено напрямую, не косвенно.
2. AARQ (73 байта, LLC-обёрнутый, содержит пароль `31323334 35363738`
   = ASCII "12345678") **подтверждается счётчиком на уровне TCP (ACK)
   уже через ~0.6с** после отправки — то есть байты гарантированно
   дошли и были приняты стеком счётчика.
3. После этого — ни одного байта от счётчика. Это НЕ похоже на
   случайный сетевой джиттер: цикл SNRM→UA→AARQ(доставлен)→тишина→
   [наш таймаут]→заново с SNRM повторялся АБСОЛЮТНО ОДИНАКОВО
   (одна и та же длительность) на протяжении всей 150-секундной
   сессии — детерминированное поведение, не случайное.

**Точечный тест по просьбе пользователя**: код изменён так, чтобы
после успешного SNRM/UA ждать AARE/GET-response С СИЛЬНО УВЕЛИЧЕННЫМ
таймаутом (45с, `DEFAULT_ASSOCIATION_TIMEOUT_MS`) и БЕЗ повторной
отправки SNRM (раз доставка AARQ уже подтверждена TCP, повторный SNRM
её не улучшит — только сбивает уже установленную DLMS-сессию).
Результат: **счётчик молчал все 45 секунд, AARE так и не пришёл.**
Это снимает гипотезу "нужно просто подождать дольше" — 45с молчания
после подтверждённой доставки запроса это уже не сетевая задержка, а,
похоже, счётчик либо не обрабатывает этот конкретный AARQ (возможно,
специфика того, как реализовано ACSE/AARQ в его прошивке для
call-home сценария), либо ожидает от Gateway что-то ещё перед тем как
ответить (например, промежуточный I-кадр/RR-подтверждение), чего
текущий код не посылает.

**Итоговый вывод по обеим находкам вместе**: есть ДВЕ РАЗНЫЕ проблемы
на разных уровнях:
- Установление TCP-соединения регулярно страдает от потери пакетов
  (см. выше, находка про SYN/SYN-ACK retransmit-штормы) — это
  инфраструктурная/сетевая проблема, вне кода.
- Даже когда соединение и HDLC-связь (SNRM/UA) успешно устанавливаются
  и AARQ гарантированно доставлен, счётчик не отвечает AARE в разумные
  сроки — это уже похоже на особенность/ограничение прошивки счётчика
  в обработке ACSE-ассоциации через call-home, а не на сетевую
  проблему и не на баг в текущей реализации протокола (протокол
  проверен побайтово и корректен).

Код и тесты (109, все зелёные) не меняются в части корректности
протокола — добавлено только более терпеливое и менее расточительное
ожидание AARE/GET-response (без лишних пересылок SNRM, см.
`read_via_call_home` в `callhome.py`). Дальнейшая диагностика (если
потребуется) должна идти в сторону протокольного анализа ACSE/AARQ,
которые не отвечает счётчик, возможно с участием производителя
оборудования — это выходит за рамки того, что можно исправить со
стороны Gateway/Backend.

Решение пользователя: call-home транспорт оставлен как есть (код
корректен и протестирован, живая нестабильность — известное
эксплуатационное ограничение конкретного счётчика/канала связи, не
блокирует дальнейшую работу). Отдельно отмечено: позже потребуется
более детально изучить сервисную программу производителя (легаси
Windows-приложение Risesun Smart Meter Manage v2.0.1.5) — вероятно,
для дальнейшей диагностики протокольных особенностей записи/AARQ.

## Этап 2 (запись параметров), итерация 1: инфраструктура + «Установить дату/время» — готово (2026-08-18)

По решению пользователя Этап 2 сделан итеративно: сначала общая
инфраструктура записи параметров + одна конкретная категория (дата/
время счётчика — явно требуется в UI по ТЗ п.4.2.11, кнопка
«Установить время»), остальные четыре категории п.4.2.4 (режимы
отображения, тарифное расписание, параметры профиля нагрузки,
параметры GPRS) — в следующих итерациях по той же инфраструктуре.

**Protocol Gateway** (`protocols/dlms.py`, `protocols/hdlc_dlms.py`):
- `build_set_request`/`parse_set_request`/`build_set_response`/
  `parse_set_response` — SET-request/response-Normal (теги 0xC1/0xC5),
  тот же принцип APDU, что и у существующего GET.
- `build_get_request`/`read_register`/`read_register_via_established_link`
  получили параметр `class_id` (по умолчанию 3 — Register) — нужен для
  чтения class-1 (Data) объектов вроде «Current Time»/«Current Date».
- Новые `write_register`/`write_register_via_established_link` —
  SNRM/UA + AARQ/AARE + SET, зеркально `read_register`, но без
  call-home (см. ниже).
- Эмулятор (`emulators/hdlc_dlms_emulator.py`) научился отвечать и на
  SET (сохраняет значение в переданный `data_values` словарь), и на GET
  class-1 объектов (читает из того же словаря) — используется в
  интеграционных тестах Gateway и в сквозной проверке ниже.
- 88 тестов Gateway (было 83), все зелёные.

**gRPC-контракт**: `WriteRegisterRequest`/`WriteRegisterResponse` +
`rpc WriteRegister`; `ReadRegisterRequest` получил поле `class_id`.
Значение кодируется на стороне Gateway по дискриминатору `value_type`
(Backend не знает DLMS-кодировку — Promt_MMWS.md, раздел 3, принцип 1);
пока поддержан только `"octet_string"` — этого достаточно для
даты/времени, остальные типы добавятся по мере следующих итераций.
**Запись через call-home намеренно не реализована** — `_do_write`
бросает `GatewayError` явно, а не тихо падает по таймауту, до отдельной
доработки/диагностики call-home транспорта (см. решение выше).

**Кодировка даты/времени — лучшее приближение, НЕ подтверждено на
реальном оборудовании**: словарь OBIS (лист RW_Tree_параметры) хранит
«Current Time» (`1.0.0.9.1.ff`) и «Current Date» (`1.0.0.9.2.ff`) как
ДВА отдельных объекта класса 1 (Data), не единый DLMS Clock (класс 8) —
уже отличие от «стандартного» DLMS. Байтовая раскладка — по листу
«Типы_данных_кодирование»: Time (Type_ID=6, формат `hhmmss`, 3 байта),
Date and Week (Type_ID=5, формат `YYMMDDWW`, 4 байта); BitType не
указан как BCD ни для одной из этих двух записей (в отличие от
энергии/тока, где BCD указан явно) — решено кодировать сырыми
двоичными байтами, не BCD. Это НЕ проверено на реальном счётчике —
подлежит сверке при первой живой попытке записи (по аналогии с тем,
как OBIS 96.80.0 для энергии был найден эмпирически, а не по
документации).

**Backend**: `ParameterWriteHistory` (миграция `00e6e74af911`) — по
ТЗ Приложение Б, поля user/meter/parameter/obis/old_value/new_value/
result/error_message, заполняется БЕЗУСЛОВНО при каждой попытке записи
(успешной или нет). Каждая запись также дублируется в общий `audit_log`
(`action="meter.write_parameter"`, `source="system"`) — ТЗ п.4.2.4
ссылается на п.4.2.7 (общий аудит), Приложение Б отдельно требует
предметный `parameter_write_history` — оба журнала ведутся параллельно,
как и для остальных операций (сравнение с `event_log`/`tamper_log`,
которые тоже отдельно от `audit_log`). `job_worker._run_write_datetime`:
читает старое значение (best-effort, ошибка чтения не блокирует
запись — `old_value` просто останется `null`), пишет новое, две строки
`parameter_write_history` (`datetime.time`/`datetime.date`) на одну
задачу. `POST /api/meters/{id}/write-datetime` — `Permission.WRITE_PARAMETER`

**Frontend**: кнопка «Установить время» на карточке счётчика (ТЗ

прогресс задачи отображается тем же WebSocket-паттерном, что и у кнопки
«Обновить показания».

**Сквозная проверка** (Backend → gRPC → Gateway → TCP, реальный
docker-стек, временный тестовый эмулятор в сети `mmws_default`,
НЕ через pytest): счётчик id=6, задача `write_datetime` дважды подряд —
`succeeded` оба раза; на втором проходе `old_value` корректно содержит

**Не сделано в этой итерации** (следующие итерации Этапа 2, та же

Сквозная проверка сделана только через временный тестовый эмулятор

## Второй счётчик (202001002352) не выходит на связь: сетевая диагностика (2026-08-19)

Пользователь предоставил параметры обоих реальных счётчиков:
202306004113 (5А, IP 10.86.31.127, регулярно звонит на call-home порт
Gateway, см. выше) и 202001002352 (100А, IP 10.86.64.172, ни разу не
подключился за всё время наблюдения этой сессии).

Прямая сетевая диагностика (ping + перебор портов) с сервера Gateway:

- **Оба IP пингуются** — ICMP отвечает, с похожим по характеру высоким
  и нестабильным джиттером (примерно 380мс — 1.5с), что согласуется с
  ранее подтверждённой картиной нестабильного канала связи (см. находки
  tcpdump выше). Сеть до обоих счётчиков в принципе доступна.
- **TTL отличается**: 125 у 202306004113, 252 у 202001002352— счётчики
  идут по разным сетевым путям/через разное промежуточное оборудование
  (не единая точка отказа на маршруте).
- **Ни один из счётчиков не принимает входящие TCP-подключения** —
  перебор портов (2009, 4059, 502, 102, 23, 80, 8080 и др., плюс nmap
  1-2000 у 202001002352) не нашёл ни одного открытого порта НИ У ОДНОГО
  из двух счётчиков, включая заведомо рабочий 202306004113. Это
  подтверждает, что «пустой список открытых портов» — норма для этой
  модели устройств (чисто call-home, входящих соединений не принимают
  вообще), а не специфичная проблема именно второго счётчика.

**Вывод**: сетевой доступ (на уровне IP) до второго счётчика есть, но
он не инициирует call-home соединение к нашему Gateway. Поскольку сеть
исправна и оба счётчика ведут себя одинаково на уровне портов, причина
отсутствия звонков — вероятно, конфигурация самого счётчика (адрес/порт

неактивен, даже если сетевой интерфейс/модем пингуется). Дальше это
нужно проверять на месте — в конфигурации самого счётчика — либо у
того, кто его изначально настраивал; с сервера Gateway дальше не
продиагностировать.

## Этап 2, итерация 2: запись номера расчётного периода (2026-08-19)

Полный перебор обоих листов словаря OBIS (`RW_Tree_параметры`,
`RW_Tree_только_с_OBIS`) подтвердил: раздел «Parameter» (запись)
содержит РОВНО пять объектов класса 1 (Data) — Current Settlement No
(`1.0.0.1.0.ff`), Current Available Settlement No (`1.0.0.1.1.ff`),
Current Time/Date/Week (первые два уже реализованы, см. итерацию 1).
Кодов для тарифного расписания (как структуры), режимов отображения и
параметров GPRS в словаре нет вообще — по Promt_MMWS.md использовать
общие DLMS-стандарты вместо словаря запрещено без согласования,
поэтому эти три категории по-прежнему не реализованы (см. итерацию 1).
Пользователь выбрал следующим шагом реализовать оставшиеся два
объекта — номера расчётного периода.

Реализация — по той же инфраструктуре, что и дата/время, но
обобщённая под будущие одиночные параметры:
- `app/services/write_parameters.py` (Backend) — реестр
  `WRITABLE_INT_PARAMETERS` (OBIS + class_id + value_type на параметр);
  единая точка правды для валидации в API и исполнения в job_worker.
- Gateway: новый `value_type="unsigned"` в `_VALUE_ENCODERS`
  (`grpc_server.py`) — переиспользует существующее поле `value_bytes`
  протокола (первый байт = значение), никаких изменений в
  `gateway.proto` не потребовалось.
- Backend: `POST /api/meters/{id}/write-parameter/{parameter}` (тело
  `{value: int}`, 0-255) — 400 для параметра вне реестра, 422 для
  значения вне диапазона; `job_worker._run_write_parameter` —
  обобщённый обработчик (читает старое значение best-effort, пишет
  новое, ведёт `parameter_write_history` + `audit_log`, тот же принцип,
  что и у `_run_write_datetime`).
- Frontend: секция «Расчётный период» на карточке счётчика — два
  числовых поля (0-255) + подтверждение перед отправкой.

**Кодировка — тоже лучшее приближение, не подтверждено на реальном
оборудовании**: 1 байт (`TAG_UNSIGNED`), диапазон 0-255 — по аналогии
с «Tariff 1..12», встречающимся в других частях словаря (не более
2 цифр), но точный диапазон/формат для «номера расчётного периода» в
словаре не уточнён явно.

Сквозная проверка через временный тестовый эмулятор (тот же приём, что
и в итерации 1): запись `settlement_no=3` → `succeeded`, повторная
запись `settlement_no=7` → `old_value=3` корректно прочитан перед
записью; `available_settlement_no=12` — тоже `succeeded`. Байты на
проводе (по логам эмулятора) — `11 03`/`11 07`/`11 0c`
(`TAG_UNSIGNED` + значение) — соответствуют ожиданиям.

Gateway: 88 тестов (без изменений в количестве — новый кодировщик не
выделен в отдельно тестируемую протокольную функцию, это простая
однострочная обёртка над уже протестированным `datatypes.encode_unsigned`).
Backend: 31 тест (было 29).

Живая проверка на реальном оборудовании — по тому же решению
пользователя, что и для даты/времени, отложена осознанно.

## Этап 3: профиль нагрузки (2026-08-19)

ТЗ п.4.2.3 — чтение буфера профиля нагрузки счётчика (получасовые/
часовые интервалы показаний за диапазон дат). Ключевое архитектурное
отличие от Этапов 1-2: буфер может быть заметно больше одного DLMS PDU
и приходить несколькими «датаблоками» (GET.response-With-Datablock +
GET.request-Next), а сама пересылка может занимать заметное время —
именно ради этого сценария изначально был выбран gRPC вместо простого
REST между Backend и Gateway (докстринг `proto/gateway.proto` формулирует
это явно: «потоковая передача данных профиля нагрузки»). Реализация
подтверждает эту причину на практике: `ReadLoadProfile` — единственный
server-streaming RPC во всём контракте.

**Адрес OBIS-объекта буфера профиля нагрузки отсутствует в словаре
OBIS.xlsx целиком** — проверены все 7 листов, есть только настройки
интервала записи (`Load Profile Interval (Min)`, уже реализовано в
Этапе 2), но не адрес самого объекта Profile Generic (класс 7). По
явному решению пользователя (AskUserQuestion, 2026-08-19) используется
стандартный DLMS-адрес «Load Profile 1» — decimal-нотация
`1-0:99.1.0.255` (IEC 62056-6-2) — как рабочая гипотеза, ПОДЛЕЖАЩАЯ
ПРОВЕРКЕ на реальном оборудовании, когда это станет возможно (сейчас
заблокировано нерешённой проблемой AARE, см. выше). В hex-нотации
проекта (то же правило decimal→hex по полям, что и в Этапе 2, итерация
3: C=99→`63`, D=1→`01`, E=0→`00`, F=255→`ff`) это
`1.0.63.1.0.ff`. Константа вынесена в
`backend/app/services/load_profile.py` (`DEFAULT_LOAD_PROFILE_OBIS`) с
возможностью переопределить её per-request через API — специально на
случай, если гипотеза не подтвердится на реальном оборудовании и
потребуется другой адрес без переразвёртывания кода.

**Протокольный слой (Gateway)**:
- `protocols/datatypes.py` — добавлены `encode_structure`/`encode_array`
  (Structure/Array Common-Data-Types, теги 0x02/0x01) и
  `encode_cosem_date_time`/`decode_cosem_date_time` (12 сырых байт:
  год/месяц/день/день-недели/час/минута/секунда/сотые/отклонение-TZ/
  статус — общая DLMS-конвенция, НЕ из словаря OBIS, не подтверждена на
  реальном оборудовании).
- `protocols/dlms.py` — `build_get_request_range()` формирует
  GET.request-Normal с access-selection=range-descriptor (selector=1):
  структура из 4 полей (restricting_object со ссылкой на стандартный
  объект Clock класс 8 OBIS `0.0.1.0.0.255`, from/to как cosem-date-time,
  пустой список колонок = «все»). `build_get_request_next()` /
  `build_get_response_datablock()` / `parse_get_response_datablock()` —
  собственный упрощённый формат кадров блочной передачи (не полный BER
  ASN.1, тот же принцип упрощения, что и у остальной части ACSE/xDLMS в
  этом PoC).
- `protocols/hdlc_dlms.py` — `read_load_profile()`: генератор, отдающий
  КАЖДУЮ строку буфера сразу по мере накопления байт из датаблоков (не
  ждёт полного ответа) — decode_value вызывается инкрементально на
  накопленном буфере, ловится `DlmsDataError` как сигнал «строка ещё не
  собрана целиком, жду следующий датаблок». Это прямая протокольная
  основа для докачки при обрыве связи (см. ниже).
- `emulators/hdlc_dlms_emulator.py` — эмулятор расширен: настраиваемые
  `load_profile_obis`/`load_profile_rows`/`load_profile_block_size`;
  распознаёт range-selector GET по совпадению OBIS и присутствию
  access-selection, ВСЕГДА отвечает через серию датаблоков (даже если
  данные уместились бы в одном PDU) — так тесты гарантированно проверяют
  именно механизм блочной передачи, а не только «короткий путь».

**Найденный и исправленный баг**: первая версия `read_load_profile()`
пропускала SNRM/UA — сразу слала AARQ поверх неустановленного HDLC-
соединения. Эмулятор (ожидающий SNRM первым кадром) молча закрывал
соединение без ответа, клиент падал с `ConnectionLostError` уже на
попытке прочитать AARE. Исправлено добавлением `_establish_link(...)`
перед AARQ — та же схема, что и в `read_register`/`write_register`.
Найдено и исправлено через интеграционный тест, не на реальном
оборудовании.

**gRPC-контракт** (`proto/gateway.proto`) — `ReadLoadProfile` возвращает
`stream ReadLoadProfileResponse`, `oneof{LoadProfileRow row, ReadError
error}` на каждое сообщение (тот же формат ошибки, что у ReadRegister/
WriteRegister). `LoadProfileRow` — Gateway САМ декодирует первую колонку
строки как cosem-date-time и отдаёт готовым `timestamp_iso` (принцип
"Backend не реализует протокольную логику" — Promt_MMWS.md, раздел 3,
принцип 1 — соблюдён и здесь: Backend получает уже готовую дату, а не
сырые 12 байт). Остальные колонки — `values_json`, JSON-совместимый вид.
Если во время потоковой передачи происходит ошибка (обрыв, таймаут),
Gateway отдаёт `error` СЛЕДУЮЩИМ сообщением потока — строки, отправленные
ДО этого момента, уже доставлены клиенту и не теряются.

**Backend — докачка при обрыве (is_partial)**: вместо отдельного
отслеживания «точки, на которой оборвались» реализован более простой и
надёжный механизм — таблица `load_profile_data` имеет уникальность
`(meter_id, obis_code, timestamp)`, вставка идёт через `INSERT ... ON
CONFLICT DO NOTHING` для каждой строки по мере получения из потока,
плюс периодический commit каждые 20 строк (ограничивает потери при
аварийном падении самого процесса воркера, не только при пойманном
исключении). Результат: повторный запуск job с тем же (или более
широким) диапазоном дат идемпотентен — уже сохранённые строки просто не
дублируются, дыр после обрыва не остаётся. `job.error.is_partial=true`
сигнализирует пользователю, что часть данных всё же сохранилась и стоит
просто повторить запрос, а не считать всю операцию полностью
провалившейся.

Job WebSocket-стрим (`/api/jobs/{id}/stream`) расширен: раньше сообщение
отправлялось только при смене `status`, теперь — ещё и при изменении
`result` (нужно для прогресс-бара: `job.result.rows_written` обновляется
на каждом коммите, до завершения задачи).

**Frontend**: новая секция «Профиль нагрузки» на карточке счётчика — выбор
диапазона дат (`<input type="datetime-local">`), кнопка запуска, прогресс
по WebSocket (принято строк N), таблица уже сохранённых строк (подгружается
при открытии страницы и после завершения задачи). Visual UI-проверку в
браузере выполнить не удалось (нет соответствующего инструмента в этой
сессии) — проверено сборкой (`tsc && vite build` внутри `node:20-alpine`,
чисто) и пользователю предложено проверить самостоятельно на
http://localhost:5173.

**Сквозная проверка через реальные Docker-контейнеры** (не только unit/
integration-тесты, а пересобранные и перезапущенные `gateway-risesun`,
`backend`, `frontend` из актуального кода): временный эмулятор с 8
строками буфера и намеренно маленьким `block_size=16` (форсирует
блочную передачу на каждую строку) запущен в сети `mmws_default`;
Backend REST API → job → gRPC-стрим → Gateway → блочная передача DLMS →
эмулятор — все 8 строк сохранены и отданы через `GET .../load-profile`

## Этап 4: автоматизация (2026-08-19)

ТЗ п.4.2.5 (схемы параметров), п.4.2.6 (расписания автоопроса), п.4.2.8
(уведомления). Этап целиком в Backend/Frontend — протокольный слой
Gateway не менялся (0 новых зависимостей/файлов в `gateway/`).

**Схемы параметров** (`parameter_schemes`): именованный набор пар
параметр→значение из уже существующего реестра `WRITABLE_INT_PARAMETERS`
(Этап 2) — `write_datetime` в схемы сознательно не включён (у него нет
пользовательского значения, всегда «сейчас»). Применение к группе
счётчиков (`POST /apply`) создаёт по одной `write_parameter` Job на
каждую пару параметр×счётчик — те же существующие путь исполнения и
аудит (`parameter_write_history`), что и у одиночной записи, без
отдельной инфраструктуры отслеживания «пакета». `job.payload` попутно
несёт `scheme_id`/`scheme_name` — не используется исполнением, но
улучшает трассируемость при разборе истории.

**Права доступа — важное уточнение по ходу работы**: исходно и создание,
и применение схем/расписаний были заведены под `WRITE_PARAMETER`
(доступно «Инженеру»). Перечитав ТЗ Приложение Б TABLE 0 внимательнее,
обнаружено явное разделение: «Инженер» — «применение схем параметров (в
том числе массовое)», а вот «управление... расписаниями автоопроса,
схемами параметров» — в перечне прав только «Администратора». Заведены
два новых пермишена (`MANAGE_PARAMETER_SCHEMES`, `MANAGE_SCHEDULED_JOBS`,
только Admin/Super-admin) — CRUD схем/расписаний требует их, а
`POST /parameter-schemes/{id}/apply` остался на `WRITE_PARAMETER`
(Engineer+). Тест `test_engineer_can_apply_but_not_manage_schemes`
фиксирует именно это разделение явно.

**Расписания** (`scheduled_jobs` + `scheduled_job_runs`): cron-выражение
(валидируется `croniter.is_valid` на входе), список ID счётчиков-группы,
тип операции (`read_current` | `read_load_profile`) с параметрами
операции (`obis` либо `window_hours` — окно каждый раз отсчитывается от
ТЕКУЩЕГО момента запуска, а не от предыдущего запуска, что проще и
устойчивее к пропущенным/задержанным тикам планировщика). `next_run_at`
сознательно НЕ хранится в БД — вычисляется на лету (`croniter` от
`cron_expression`+`last_run_at`) при каждой сериализации, чтобы
редактирование cron-выражения не могло рассинхронизироваться с
персистентным полем.

Фоновый цикл `scheduler_loop` (интервал `scheduler_check_interval_s`,
30с) по срабатыванию создаёт `ScheduledJobRun` + по одной обычной `Job`
на каждый счётчик группы — сам планировщик счётчики не читает, эту
работу делает штатный `job_worker` (то же разделение ответственности,
что и у ручного запуска через API). Когда ПОСЛЕДНЯЯ дочерняя Job запуска
завершается, `job_worker._maybe_finalize_scheduled_job_run` сводит итог
(`succeeded`/`partial_failure`/`failed`) и при наличии ошибок создаёт
уведомление `scheduled_job_failed`. Небольшая, осознанно принятая гонка:
при нескольких экземплярах Backend два процесса могут почти одновременно
увидеть «все дочерние задачи завершены» — проверка `run.status !=
RUNNING` защищает от двойной финализации в подавляющем большинстве
случаев; для PoC-масштаба системы отдельная блокировка сочтена
избыточной (задокументировано в коде, не скрыто).

**Уведомления** (`notifications`, ТЗ п.4.2.8) — три категории:
- `meter_offline` — фоновый `offline_detector_loop` (интервал
  `notification_check_interval_s`, 60с) сравнивает `last_seen_at` с
  настраиваемым таймаутом (`settings.meter_offline_timeout_s`, та же
  величина теперь используется и в `Meter.is_online` — раньше там был
  отдельный хардкод 3600, разъехавшийся с ТЗ «настраиваемый таймаут»).
  Edge-triggered без отдельного состояния в памяти: guard — «есть ли уже
  notification для этого счётчика с `created_at > last_seen_at`» —
  не плодит повтор на каждый тик, но корректно создаёт новое уведомление
  после того, как счётчик снова вышел на связь и ушёл в offline повторно.
- `scheduled_job_failed` — см. выше.
- `tamper_event` — **только инфраструктура, ничем не порождается**.
  Чтение журнала вмешательств со счётчика (ТЗ п.4.2.3) не реализовано ни
  в одном из этапов — таблица `tamper_log` всегда пуста. В словаре OBIS
  для этого нашёлся не буфер-профиль (как для профиля нагрузки), а набор
  счётчиков/длительностей по категориям событий (лист
  `Events_Tamper_коды`, ~670 строк, структура `{категория} → {Counter,
  Duration}` для каждой из 11 категорий) — принципиально другая по форме
  протокольная задача, чем всё, что уже реализовано (Этапы 1-3 читали
  Register/Data/Profile Generic, не разбирали дерево вложенных
  счётчиков). Решение пользователя (AskUserQuestion, 2026-08-19):
  реализовать в Этапе 4 только инфраструктуру уведомлений, само чтение
  tamper-log — отдельная будущая задача.

Уведомления общесистемные, не персональный inbox на пользователя (ТЗ не
описывает разный набор уведомлений по ролям) — `is_read` общий флаг,
отметить прочитанным может любой пользователь с правом просмотра.
Доставка в реальном времени — `WS /api/notifications/stream`, тот же
паттерн, что и `/api/jobs/{id}/stream` (поллинг БД раз в 2с, не
LISTEN/NOTIFY — сознательное следование уже принятому в проекте стилю
вместо смены техники ради одной фичи). Попутно расширен
`/api/jobs/{id}/stream`: раньше отправлял сообщение только при смене
`status`, теперь — ещё и при изменении `result` (нужно для прогресс-бара
на долгих операциях типа профиля нагрузки — сам факт замечен по ходу
работы над Этапом 4, не специфичен для уведомлений, но правился здесь же).

**Новая зависимость**: `croniter==2.0.5` (парсинг/вычисление cron —
общепринятая, компактная библиотека, не переизобретать).

## Этап 5: биллинг-интеграция и завершающая доработка (2026-08-19)

ТЗ п.4.2.9 (интеграция с биллингом), п.4.2.10 (удалённое отключение/
подключение), реализовано **строго по техрегламенту API.docx**, плюс
завершение оставшихся экранов ТЗ п.4.2.11 (Дашборд, Журнал аудита,
Управление пользователями) в рамках «завершающей доработки»
(Promt_MMWS.md, Этап 5 — «Мониторинг, экспорт, финальное тестирование»).

**Disconnect Control (ACTION-сервис DLMS)** — та же ситуация, что и с
профилем нагрузки в Этапе 3: адрес объекта (класс DLMS 70) нигде не
задокументирован в словаре OBIS.xlsx (проверено все 7 листов по
disconnect/relay/отключ/реле). По решению пользователя (AskUserQuestion,
2026-08-19) используется стандартный DLMS-адрес — decimal
`0-0:96.3.10.255` → hex-нотация проекта `0.0.60.3.a.ff` (то же правило
перевода decimal→hex по полям, что и в Этапах 2/3) — как рабочая
гипотеза, требующая проверки на реальном оборудовании. В протокольном
слое Gateway впервые реализован ACTION-request/response (Green Book) —
`build_action_request`/`parse_action_response` в `protocols/dlms.py`,
тот же принцип упрощённого APDU (фиксированные позиции полей вместо
полного BER), что и у GET/SET. `hdlc_dlms.execute_action()` — SNRM/UA +
AARQ/AARE + ACTION, методы `remote_disconnect`(1)/`remote_reconnect`(2).
Новый gRPC RPC `DisconnectMeter` (unary) — синхронный, как
ReadRegister/WriteRegister; асинхронность (Job, batch_id) — на стороне
Backend.

**Единый обработчик disconnect/reconnect** (`job_worker._run_disconnect_
operation`) используется ОБОИМИ путями инициации (ТЗ п.4.2.10):
ручной запуск с карточки счётчика (`POST /api/meters/{id}/disconnect`
/`/reconnect`, Permission.WRITE_PARAMETER — тот же набор ролей
Инженер/Администратор, что и у записи параметров) и пакетная операция
от биллинга. Источник инициации (`job.payload["source"]` = "web" |
"billing", плюс `batch_id` для пакетных) передаётся в `audit_log`
безусловно при КАЖДОЙ попытке (успешной или нет) — прямое требование
ТЗ п.4.2.10 «безусловная фиксация... с указанием источника инициации».

**Пакетные операции биллинга** (`disconnect_batches`/
`disconnect_batch_items`) архитектурно — прямое повторение схемы
`ScheduledJob`/`ScheduledJobRun` из Этапа 4: пакет порождает по одной
обычной `Job` на каждый счётчик, сам не читает/не пишет на счётчики.
`job_worker._maybe_finalize_disconnect_batch_item` (тот же паттерн, что
`_maybe_finalize_scheduled_job_run`) обновляет статус элемента и, когда
это была последняя незавершённая задача пакета, финализирует сам пакет
(`completed`/`completed_with_errors`/`failed` — коды статуса и семантика
«частичный отказ — штатная ситуация» взяты дословно из API.docx п.4.5,
п.7). Счётчики с неизвестным серийным номером получают статус `failed`,
`error_code="METER_NOT_FOUND"` СРАЗУ при создании пакета, без Job —
`finalize_batch_if_complete` вызывается сразу после создания элементов
именно ради этого крайнего случая (пакет, где ВСЕ счётчики неизвестны,
иначе никогда не финализировался бы — не от кого получить событие
завершения Job).

**Идемпотентность** (API.docx п.2.3) — `UNIQUE(api_key_id,
idempotency_key)`. Повтор с тем же ключом И тем же телом запроса
(сверка по набору серийных номеров и операции) возвращает уже принятый
`batch_id` без повторной постановки в очередь. Тот же ключ с ИНЫМ телом
— `DUPLICATE_IDEMPOTENCY_KEY` (400). Ограничение размера пакета (500
счётчиков, раздел 6 API.docx) намеренно проверяется вручную в
`billing.py`, НЕ через `Field(max_length=500)` в pydantic-схеме — иначе
превышение ловилось бы как обычная ошибка валидации ДО тела обработчика
и отдавало бы общий `VALIDATION_ERROR` вместо специфичного
`BATCH_TOO_LARGE` (найдено и исправлено по ходу написания тестов).

**Аутентификация биллинга** — полностью отдельная от JWT веб-сессий
(`app/auth/billing_deps.py`), `Authorization: Bearer <API-ключ>`.
Секрет хешируется bcrypt (та же библиотека, что и пароли пользователей,
переиспользована для другого типа секрета — ключ генерируется на
сервере `secrets.token_urlsafe(32)`, а не выбирается человеком, поэтому
общий механизм хеширования подходит без изменений) и отдаётся
администратору РОВНО ОДИН РАЗ, в момент выдачи (`POST /api/billing-
keys`) — далее восстановить его нельзя, только отозвать и выдать новый.
Поиск ключа по предъявленному секрету — перебор активных ключей с
`verify_password` (хеш не подлежит поиску по индексу); осознанно
приемлемо при ожидаемом малом числе биллинг-интеграций (ТЗ описывает
«выделенную техническую учётную запись», не массовую аутентификацию).

**Rate limiting** (60 запросов/мин на ключ по умолчанию, ТЗ раздел 6
API.docx, настраивается индивидуально на уровне ключа) — скользящее
окно **в памяти процесса** (`_REQUEST_LOG` в `billing_deps.py`), 429 +
заголовок `Retry-After`. **Известное отступление от ТЗ п.4.6**
(горизонтальное масштабирование Backend): при нескольких экземплярах
Backend лимит проверяется независимо на каждом — фактический совокупный
лимит может быть выше номинального в N раз. Тот же принцип осознанного
упрощения, что и у финализации запуска расписания в Этапе 4; в проде
следует вынести в общее хранилище (Redis INCR+EXPIRE). Задокументировано
в коде явно, не скрыто.

**Единый формат ошибок** (API.docx раздел 5) — `BillingApiError` +
глобальный `exception_handler` в `main.py`, плюс отдельный перехват
`RequestValidationError` (иначе FastAPI вернул бы СВОЙ формат
`{"detail": [...]}` до того, как код эндпоинта успел бы отработать, —
найдено при написании теста на отсутствующий обязательный параметр).
Оба обработчика активны ТОЛЬКО для путей `/api/v1/billing/*` — обычный
API веб-интерфейса не затронут. `X-Request-Id` — заголовок на КАЖДОМ
ответе сегмента (успешном и ошибочном), генерируется middleware;
`error.request_id` в теле — только для ошибок (сверено дословно с
примерами API.docx раздела 5).

**GET /tariffs — честный пробел, не имитация.** Контракт эндпоинта
(аутентификация, валидация `meter_ids`/`region`, пагинация, формат
ответа) реализован полностью, но всегда возвращает пустой `items` —
чтение полного тарифного расписания (таблица зон/ставок) со счётчика не
реализовано ни в одном из этапов; Этап 2 реализовал только
`weekend_rate_type` — один числовой селектор типа тарифа выходного дня,
а не структуру, представимую в формате API.docx (`zone`/`rate`/`from`/
`to`). Тот же принцип, что и `tamper_event` в Этапе 4 — инфраструктура
без источника данных, задокументировано явно, не подменено фиктивными
данными.

## Этап 6: обнаружение новых счётчиков (2026-08-19)

Не из исходного плана Promt_MMWS.md (Этапы 0-5) — обнаружен пользователем
как реальный пробел уже после формальной сдачи Этапа 5: до этого момента
добавить счётчик можно было только вручную, заранее зная его серийный
номер, IP и т.д. Для call-home счётчиков (звонят сами — расхождение с
ТЗ Table 1, см. записи от 2026-08-18) это нереалистично — оператор
физически не может заранее знать серийный номер только что
установленного на объекте счётчика.

**Ключевое техническое основание** — уже существующий с Этапа 1 механизм
`callhome.CallHomePool._identify()` УЖЕ умеет опознавать ПОЛНЫЙ серийный
номер любого позвонившего счётчика по DL/T645-анонс-кадру
(`serial_from_dlt645_address`), причём БЕЗ необходимости заранее знать
этот номер — только раньше эта информация использовалась исключительно
для внутреннего сопоставления `claim(serial)` и нигде не сообщалась
наружу. Этап 6 просто открывает то, что Gateway и так уже знал.

**Развилка, вынесенная на решение пользователя**: живая смена порта
call-home в панели суперадминистратора (без перезапуска Gateway) —
против простого сохранения значения, применяемого при следующем
перезапуске. Выбран первый, более сложный вариант (AskUserQuestion,
2026-08-19) — технически он оказался вполне посильным благодаря тому,
что `CallHomePool` с самого начала имел чистые `stop()`/`start()`.

**Gateway**:
- `callhome.CallHomePool` — добавлен `_seen_serials: dict[serial, first_seen_unix]`,
  независимый от скользящего окна held-соединений (то, что вытесняется
  окном — это TCP-соединения, а не сам факт «этот серийник когда-то
  звонил»). Метод `list_seen_serials()`.
- Новый gRPC RPC `ListCallHomeSerials` — Backend периодически опрашивает
  (см. ниже).
- Новый gRPC RPC `SetCallHomePort` — `CallHomePool.stop()` старого пула +
  `CallHomePool(bind_port=новый).start()`, атомарная подмена ссылки под
  локом (`_call_home_lock`, защита от гонки при параллельных RPC-вызовах
  в пуле потоков `grpc.server`). Подтверждено вживую через реальные
  контейнеры: старый порт закрывается, новый открывается, БЕЗ
  перезапуска процесса/контейнера.
- `HealthCheckResponse` расширен полем `call_home_port` — Backend
  получает ФАКТИЧЕСКИЙ порт на каждом heartbeat (не только когда меняли
  через панель — например, и после перезапуска контейнера с другим
  значением переменной окружения `MMWS_CALL_HOME_PORT`).

**Backend — модель**: `MeterStatus` (`installed`/`active`) на `Meter`,
явно НЕ то же самое, что существующий `is_active` (тот управляет
ортогональным смыслом «включён/выключен из обслуживания» для уже
полностью настроенного счётчика, применяется вместо удаления при
наличии истории — см. Этап 1). `protocol_profile`/`password_encrypted`
сделаны NULLABLE — единственные два поля, которые Gateway принципиально
не может узнать из самого факта звонка домой (DL/T645-анонс несёт
только адрес, не пароль DLMS и не протокольный профиль). `Gateway.
call_home_port` — фактический порт, отражается на каждом heartbeat.

**Обязательная защита от падения на NULL**: поскольку `protocol_profile`/
`password_encrypted` теперь могут быть NULL, все эндпоинты, ставящие
Job (`read`, `write-datetime`, `write-parameter`, `disconnect`,
`reconnect`, `read-load-profile`), теперь проходят через общий
`_get_active_meter_or_error()` — отклоняют попытку операции над
`status=installed` счётчиком понятной ошибкой 400 ДО постановки задачи в
очередь, а не позволяют job_worker упасть на `decrypt_secret(None)`.

**Фоновый цикл обнаружения** (`meter_discovery_loop`, интервал 30с, тот
же паттерн, что и `heartbeat_loop`/`scheduler_loop`): опрашивает
`ListCallHomeSerials` на каждом APPROVED Gateway, для серийников, ещё не
присутствующих в `meters` (проверка глобальная по всей таблице, не по
конкретному Gateway — serial_number уникален во всей системе), создаёт
`Meter(status=INSTALLED, is_call_home=True)`. Недоступность одного
Gateway не останавливает цикл и не мешает другим.

**Активация** (`POST /api/meters/{id}/activate`) — единственный способ
перевести `installed` в `active`; требует пароль и протокольный профиль
(оба обязательны, остальные поля — IP/порт/локация/модель —
опциональны). `Permission.MANAGE_METERS` (Админ/Супер-админ, ТЗ
Приложение Б TABLE 0 — тот же уровень прав, что и создание/
редактирование счётчиков вручную).

**Управление call-home портом** (`PUT /api/gateways/{id}/call-home-port`,
`Permission.MANAGE_GATEWAYS` — ИСКЛЮЧИТЕЛЬНО Супер-администратор, как и
весь остальной реестр Gateway по ТЗ п.4.1.1) — значение в БД сохраняется
ТОЛЬКО если Gateway подтвердил успешное переслушивание (502, если
недоступен либо явно отклонил); до этого Этапа страницы управления
Gateway во Frontend не существовало вообще (регистрация делалась через
прямые вызовы API) — заведена с нуля вместе с этой возможностью.

**Frontend**: список счётчиков сгруппирован на две секции — «Установленные
(ожидают активации)» (форма активации: протокол, пароль, местоположение)
и «Активные» (прежняя таблица без изменений). Новая страница «Gateway»
(регистрация, подтверждение/отключение, живая настройка call-home
порта) — видна только Супер-администратору.

**Сквозная проверка через реальные Docker-контейнеры** (пересобранные
`gateway-risesun`/`backend`/`frontend`): живая смена порта call-home
подтверждена на уровне TCP (старый порт `Connection refused`, новый —
`OPEN`, без перезапуска контейнера); симуляция звонка домой РАНЕЕ
НЕИЗВЕСТНОГО серийного номера (`999888777666`, отправлен на новый порт)
— в течение одного тика `meter_discovery_loop` (30с) счётчик появился в
`GET /api/meters` со `status=installed`; активация через API перевела
его в `status=active`. Также подтверждено, что уже ЗНАКОМЫЙ серийный
номер (один из реальных call-home счётчиков, зарегистрированных вручную
в более ранних этапах) НЕ дублируется при повторном обнаружении.
Тестовые данные (порт возвращён на 2009, тестовый счётчик деактивирован)
после проверки приведены в порядок.

## Этап 6.1: анализ сервисной программы завода (obwiy.zip) — коррекция профиля нагрузки (2026-08-19)

Пользователь передал `obwiy.zip` — реальную сервисную Windows-программу
завода (.NET, на базе библиотеки Gurux.DLMS), содержащую полные
экспорты COSEM-модели объектов для счётчика **DTZY217** (три исполнения:
100V/5A, 380V/5A, 380V/100A) — то есть настоящую объектную модель
прошивки, а не гипотезу по стандарту DLMS. Анализ (см. XML-экспорты,
`<GXDLMSProfileGeneric>`/`<CaptureObjects>`) дал два расхождения с
рабочими гипотезами Этапов 3 и 5:

**Профиль нагрузки — OBIS и структура буфера скорректированы.**
Реальный объект — decimal `1-1:99.1.0.255` (hex-нотация проекта
`1.1.63.1.0.ff`), не `1.0.63.1.0.ff` (поле B ошибочно было 0 вместо 1
— проверено по всем трём вариантам DTZY217, объект помечен `Version=1`
во всех). Захватываемые колонки (`CaptureObjects`) — 11 Register-
значений (3×напряжение, 3×ток, 3×cos φ, 1×служебный регистр, 1×
накопленная энергия) — объект Clock СРЕДИ НИХ ОТСУТСТВУЕТ, то есть
строка буфера не несёт метку времени сама по себе (в отличие от
предположения Этапа 3, что первая колонка — всегда 12-байтовый
cosem-date-time).

Реализовано (`gateway/src/mmws_gateway/protocols/hdlc_dlms.py`,
`dlms.py`, `grpc_server.py`, `backend/app/services/load_profile.py`):
перед чтением диапазона Gateway отдельным GET читает атрибут 4
объекта (`capture_period`, секунды) и вычисляет метку времени каждой
строки как `from_dt + номер_строки * period`; `read_load_profile()`
разбит на установление связи + `read_load_profile_via_established_link()`
(общая протокольная логика, переиспользуется и call-home транспортом).
`LoadProfileRow` в gateway.proto не поменял формат (те же
`timestamp_iso`/`values_json`), обновлены только комментарии.

**Call-home транспорт для ReadLoadProfile реализован впервые** (до
этого не существовал вовсе — `raise GatewayError("...пока не
реализован")`). `callhome.read_load_profile_via_call_home()` — тот же
приём перебора held-соединений и повтора SNRM, что и у
`read_via_call_home` (чтение регистра), но выполняет ВЕСЬ обмен чтения
буфера (GET capture_period + GET с диапазоном + датаблоки) на одном
удержанном соединении целиком; при обрыве посреди буфера — полный
повтор на следующем соединении (докачка с точки обрыва протоколом не
поддержана, но повторные строки безвредны — Backend дедуплицирует по
`(meter_id, obis, timestamp)`). Обнаруженная и исправленная по ходу
живого тестирования гонка: внутренний бюджет Gateway (`max_wait_s`)
может истечь ПОСЛЕ старта последней попытки (дедлайн проверяется
только МЕЖДУ попытками, не обрывает уже начатое ожидание ответа на
`association_timeout_ms`=45с) — из-за этого клиентский gRPC-таймаут
Backend'а (было 160с, как у чтения регистра) иногда обрывал вызов
раньше, чем Gateway успевал отдать свою, понятную ошибку; увеличено до
220с для профиля нагрузки специально (`job_worker.py`).

**Живая проверка на реальном оборудовании (2026-08-19, 2 счётчика,
202306004113 и 202001002352, через call-home)**: механизм подбора
held-соединения и полного обмена работает штатно — несколько попыток
дошли до AARE (принято) и получили настоящий GET-response. **Прямое
подтверждение гипотезы OBIS**: `1.1.63.1.0.ff` — реальный, адресуемый
объект (AARE принят, GET-response получен, а не «объект не найден»).
**Найдена новая проблема**: GET атрибута 4 (`capture_period`) на ДВУХ
разных реальных счётчиках возвращает явную DLMS data-access-error, код
`0xFA` (250, "other-reason" по Green Book) — то есть период записи
через этот путь на реальном железе не читается, хотя сам объект
профиля существует и отвечает. Полного успешного чтения буфера на
реальном оборудовании добиться не удалось (см. Disconnect Control ниже
— решение по духу то же: помечено как требующее доработки, не скрыто
за «готово»).

**Возможный обходной путь, НЕ проверенный до конца**: в словаре

дереву (не по стандарту DLMS) параметр «Load Profile Interval (Min)» —
`1.0.0.8.4.ff`, класс 1 (Data), уже используемый как ЗАПИСЫВАЕМЫЙ
(`write_parameters.py`). Чтение этого объекта — обычный одиночный GET
(тот же путь, что уже используется для чтения регистров), а не новый
многошаговый обмен по Profile Generic — потенциально надёжнее
`capture_period`. Две попытки прочитать его через call-home на реальных
счётчиках 2026-08-19 не завершились (обе — таймаут связи ДО получения
ответа, не data-access-error) — то есть результат по существу пока не
получен, требуется ещё живая проверка.

**Disconnect Control (Этап 5) — вероятно не поддержан на этой модели.**

код Этапа 5 оставлен как есть (гипотеза `0.0.60.3.a.ff` была явно
принята как непроверенная), но теперь явно задокументировано: скорее
всего эта модель счётчика не поддерживает удалённое отключение через
стандартный DLMS-объект.

## Найденный и исправленный баг: показания без масштаба (scaler) (2026-08-19)

Пользователь сообщил: показание `4507.70` отображается в MMWS как
`450770` — то есть без десятичной точки. Причина — атрибут 3 COSEM-
объекта Register (`scaler_unit`, структура `{scaler: int8, unit: enum}`)
упоминался в докстринге `dlms.build_get_request` ещё с Этапа 0
(«подтверждено реальным трафиком Risesun — легитимный клиент читает
scaler_unit отдельным GET перед value») как НАБЛЮДЕНИЕ, но реально
нигде не читался и не применялся — `read_register`/

целое число как есть, без домножения на `10^scaler`. Баг затрагивал

любой Register-объект с ненулевым scaler.

сырое значение атрибута 2 для объекта класса Register (класс 3),

GET — актуально для параметров класса Data, читаемых через тот же
код с явным `class_id=1`, например `settlement_no`) — возвращается
исходное сырое значение без изменений, ошибка не пробрасывается наверх.

call-home (общая функция `read_register_via_established_link`,
переиспользуемая `callhome.read_via_call_home`).

Эмулятор (`emulators/hdlc_dlms_emulator.py`) расширен: после ответа на
GET атрибута 2 объекта класса Register дожидается и отвечает на
следующий GET атрибута 3 (новый параметр `register_scalers` — словарь
OBIS -> scaler, по умолчанию 0, то есть старые тесты с сырыми
значениями без масштаба не изменили поведение). Новый тест
`test_register_read_applies_scaler` — сырое `450770` при `scaler=-2`
превращается в `4507.7` (то есть ровно повторяет сообщённый
пользователем баг и подтверждает исправление).

Тесты: Gateway 118 -> 120 (+2: `test_register_read_applies_scaler`,
`test_register_read_without_scaler_stays_integer`); один существующий
тест call-home (`test_read_via_call_home_succeeds_after_ignored_snrm_attempts`)
обновлён под новый двухшаговый обмен. Backend/Frontend изменений не
потребовалось — `value_json` (JSONB) одинаково хорошо хранит и int, и
float, отображение уже общее (Promt_MMWS.md, раздел 3, принцип 1:
протокольную семантику знает только Gateway).

живое, ожидает следующего реального чтения регистра для визуального
подтверждения на живом счётчике (не проверено на реальном железе на

## Тот же баг снова на живом счётчике: value и scaler_unit по разным OBIS (2026-08-20)

Пользователь сообщил повторно: на живом счётчике `202306004113`,
интерфейс Супер-администратора, чтение по OBIS `1.1.1.8.0.ff` (время
19.08.2026 13:44:01) снова показало `450770` вместо `4507.70` — то
есть предыдущее исправление (см. выше, применялось одинаково к любому
OBIS) для этого конкретного регистра не сработало на реальном
оборудовании, хотя было подтверждено эмулятором.

**Причина**: этот регистр (суммарная активная энергия) на счётчике
Risesun DTZY217 — особый случай, задокументированный ещё в первом pcap
(см. выше, п.6): value (атрибут 2) и scaler_unit (атрибут 3) одного и
того же физического регистра реально лежат на РАЗНЫХ OBIS —
scaler_unit на стандартном `1.8.0` (`1.1.1.8.0.ff`), value на
вендорском `96.80.0` (`1.1.60.50.0.ff`). Прежнее исправление читало
оба атрибута ПО ОДНОМУ И ТОМУ ЖЕ OBIS (переданному вызывающим кодом,
для этого показания — стандартному `1.1.1.8.0.ff`); на реальном
счётчике это возвращает сырое value без ошибки, но не даёт корректный
scaler_unit для НЕГО ЖЕ — точный механизм отказа (data-access-error
или просто scaler=0/некорректная структура на этом OBIS) не выяснен,
не было возможности перепроверить в реальном времени, только по
результату (значение осталось немасштабированным).

**Исправление**: `dlms.py` — новая таблица `VALUE_OBIS_OVERRIDES:
dict[str, str]`, единственная подтверждённая реальным трафиком запись
`"1.1.1.8.0.ff" -> "1.1.60.50.0.ff"`. `hdlc_dlms.
read_register_via_established_link` теперь для value (атрибут 2)
подставляет `VALUE_OBIS_OVERRIDES.get(obis, obis)` вместо запрошенного
`obis` напрямую, а scaler_unit (атрибут 3) по-прежнему запрашивает
ровно по исходному, переданному `obis` — воспроизводит единственную
подтверждённую реальным трафиком легитимного приложения комбинацию
(scaler с `1.8.0`, value с `96.80.0`), без изменений API Backend'а/
Frontend'а (оба продолжают запрашивать стандартный `1.1.1.8.0.ff`,
Promt_MMWS.md, раздел 3, принцип 1 — протокольную семантику знает
только Gateway).

Эмулятор (`hdlc_dlms_emulator.py`) — `_serve_register_scaler_followup`
раньше искал scaler по OBIS ПЕРВОГО (value) запроса; теперь ищет по
OBIS, реально указанному во ВТОРОМ (scaler) запросе — до этой правки
эмулятор не мог отличить разные OBIS для value/scaler. Три существующих
теста (`test_integration_hdlc_dlms.py`, `test_integration_mode_e.py`,
`test_cli.py`, `test_callhome.py`), использовавшие `1.1.1.8.0.ff` как
родовой «любой» OBIS для проверки несвязанной логики, переключены на
`1.1.1.7.0.ff`, чтобы не попадать под новый override случайно. Новый
тест `test_register_read_applies_value_obis_override_for_risesun_energy`
— два разных GET (value на `1.1.60.50.0.ff`, scaler на `1.1.1.8.0.ff`)
дают верно масштабированный результат `4507.7`.

Тесты: Gateway 120 -> 121 (+1). Backend/Frontend без изменений.

Как и в первый раз — исправление не проверено на реальном железе на
момент записи (только эмулятором), одна подтверждённая реальным
трафиком связка OBIS применена как единственная известная рабочая;
остаётся открытым вопросом, почему value/scaler_unit по одному OBIS не
работают вместе на этом счётчике — эмпирически подтверждённого объяснения
нет.

## Массовая активация 141 счётчика по call-home: чтение не работало, причина — не пароль (2026-09-07)

После массовой активации всех 141 автообнаруженных по call-home

полный дамп логов Gateway (контейнер пишет ~15-20 строк/сек уже 2
недели, счётчик соединений за 23000+/сутки) через `grep | tail`
оборвался на старом куске лога и создал впечатление, что опознавание
счётчиков по call-home сломано с 1 сентября — при точечной проверке
(`docker compose logs --tail=N`) опознавание оказалось рабочим
постоянно, проблема была только в том, что 150-секундное окно
ожидания конкретного джоба чтения не всегда попадало на момент
реального звонка нужного счётчика (плотный поток соединений на порт
2009 — окно из 10 held-соединений вытесняется за секунды).

**Байтовая диагностика** (`tcpdump` на порт 2009, сопоставление
`conn_no`/peer из логов Gateway с TCP-сессией в pcap, ручная и через
`HdlcFrame.decode()`) показала: HDLC-уровень (SNRM -> UA) отрабатывал
исправно, а DLMS-уровень (AARQ с паролем) — тишина: счётчик TCP-ACK'ил
пакет с AARQ, но не присылал ни AARE, ни отказ, соединение падало по
`association_timeout_ms`.

**Ошибочная гипотеза, проверенная и отвергнутая**: по указанию
пользователя клиентский HDLC-адрес (`client_addr`, ранее фиксированный
`DEFAULT_CLIENT_ADDRESS = 0x30`) был временно заменён на значение,
вычисляемое так же, как физический адрес счётчика — последние 5 цифр
серийного номера (`hdlc_dlms.py`, 6 функций). Байтовая проверка (тот
же `tcpdump` + `HdlcFrame.decode()`) показала, что с этим изменением
счётчик перестал отвечать даже на SNRM (15 попыток подряд, ни одного
UA) — стало строго хуже, чем было. Изменение отменено (`git checkout`),
код `hdlc_dlms.py` вернулся к исходному состоянию с общим
`DEFAULT_CLIENT_ADDRESS`.

**Настоящая причина и подтверждение**: пользователь предоставил
архив `ver2.zip` — оригинальный дистрибутив заводской сервисной
программы Risesun (`IECMeterManage.exe`, Ver2.0.6.0, «Risesun Smart
Meter Manage»). В `Config.ini` этого дистрибутива, секция `[DLMS]`:

```ini
MasterAddr =48
AAREPwd =12345678
```

`MasterAddr=48` — это ровно `0x30`, то есть подтверждает, что
существовавший в коде фиксированный `DEFAULT_CLIENT_ADDRESS` был
верен с самого начала (отвергнутая гипотеза выше была неверной
интерпретацией понятия «логин» на HDLC-уровне). `AAREPwd=12345678`
подтверждает, что пароль, применённый при массовой активации, тоже
был верным изначально. Таким образом ни пароль, ни адресация не были

После пересборки Gateway (код идентичен состоянию до эксперимента с

## Показания снова без дробного разделителя: порядок GET value/scaler_unit имел значение (2026-09-07)

Пользователь сообщил (со ссылкой на предыдущую сессию): показания
счётчиков по-прежнему приходят без дробного разделителя — например,
`450770` вместо `4507.70`. Проверка БД (`meter_readings`) подтвердила:
ВСЕ 13 сохранённых показаний, включая прочитанные уже ПОСЛЕ фикса
`VALUE_OBIS_OVERRIDES` (commit `bbff428`, показание id=7,
`4508010`, 2026-08-19 16:00) и все 6 показаний массовой активации
141 счётчика (id=8–13, записи из раздела выше — `6101020`, `16358300`,
`2206210`, `3992020`, `6658530`, `9783100`) — сырые целые без
масштабирования. То есть находка о «6 успешных чтениях» выше проверяла
только факт успешного чтения, а не корректность масштаба — старый баг
продолжал молча воспроизводиться.

**Диагностика**: в `hdlc_dlms.read_register_via_established_link`
добавлено логирование результата GET scaler_unit (успех/ошибка/
неожиданная структура). Пересборка и попытки живого чтения (6 job'ов
подряд на счётчиках `202302003956`/`202306004107`/др. из тех же 141) —
все 6 упали по `TIMEOUT` уже на уровне SNRM/AARQ (до достижения
изменённого кода), то есть подтвердить фикс живым трафиком в этой
сессии не удалось — текущая call-home сессия здесь оказалась
нестабильна (согласуется с ранее описанной проблемой тайминга call-home
окна, не связано с данным багом).

**Причина, по которой не хватало живого трафика для доказательства —
найдена по факту в самом коде**: докстринг `dlms.py` у
`REGISTER_SCALER_UNIT_ATTRIBUTE` с самого Этапа 0 фиксирует
подтверждённое реальным трафиком поведение легитимного заводского
клиента — «читает scaler_unit ОТДЕЛЬНЫМ GET ПЕРЕД value». Однако
реализация `read_register_via_established_link` во всех версиях,
включая версию с `VALUE_OBIS_OVERRIDES`, делала наоборот: сначала GET
value (атрибут 2), потом GET scaler_unit (атрибут 3). На эмуляторе
порядок запросов не имеет значения (эмулятор просто отвечает на любой
GET, каким бы он ни был), поэтому все тесты проходили и создавали
ложную уверенность, что масштабирование работает — реальные счётчики
на порядок запросов, по всей видимости, реагируют иначе (что именно
происходит на стороне счётчика при «неправильном» порядке — тайм-аут,
data-access-error или просто игнор второго GET — не установлено,
эмпирическая проверка недоступна в этой сессии по причине текущей
нестабильности call-home).

**Исправление**: `hdlc_dlms.read_register_via_established_link` — для
объектов класса Register порядок запросов поменян на
scaler_unit-затем-value (для класса Data, `class_id=1`, поведение не
изменилось — по-прежнему один GET value, scaler_unit не запрашивается
вовсе). `hdlc_dlms_emulator.py` — `serve_hdlc_dlms_session` теперь
различает первый GET по `attribute_id` (3 → scaler_unit, обслуживается
`_serve_register_scaler_then_value`, которая тут же дожидается второго
GET на value, возможно по другому OBIS через override) вместо прежнего
предположения «первый GET — всегда value». Инъекция ошибок
(`force_crc_error`/`force_partial_disconnect`) перенесена на первый
реально отправляемый кадр (теперь это scaler_unit) — семантика тестов
не изменилась. `test_callhome.py` — ручной эмулятор сессии в
`_serve_rest_of_session` переставлен в тот же порядок. Логирование
результата чтения scaler_unit (успех/ошибка/scaler=0/применённый
масштаб) оставлено в коде — полезно для диагностики следующего живого
чтения, когда call-home снова станет стабильным.

Тесты: Gateway 121/121 зелёные (полный прогон, включая ранее
проходившие `test_register_read_applies_scaler` и
`test_register_read_applies_value_obis_override_for_risesun_energy` —
проверено, что оба сценария (общий scaler и вендорский OBIS-override)
по-прежнему дают верно масштабированный результат при новом порядке
запросов).

Схема БД (`meter_readings.value_json` JSONB, `unit` nullable
`varchar`) уже допускает и целые, и дробные значения — изменений схемы
не потребовалось.

**Не подтверждено на реальном оборудовании** в этой сессии (см. выше
про 6 таймаутов подряд) — как и предыдущая попытка того же фикса,
это исправление построено на прямом документированном наблюдении
реального трафика (порядок GET у легитимного клиента), но по факту
проверено только эмулятором. Следующее живое чтение любого из 141
счётчика будет первой реальной проверкой; лог теперь достаточно
подробен, чтобы по нему сразу было видно, сработало исправление или
нет.

## «Что-то на китайском, не пакетами» при чтении профиля — фильтрация DL/T645-шума не переживала первый кадр (2026-09-07)

Пользователь сообщил: при чтении профиля нагрузки счётчик передаёт
«что-то на китайском», не разбираемое на пакеты — не видно ни начала,
ни конца. Попытка воспроизвести живым чтением (`read-load-profile` на
call-home счётчике `202306004107`, с параллельным `tcpdump` на порту
2009) снова не попала в окно звонка (`TIMEOUT` на SNRM) — вживую в
этой сессии не воспроизведено, но в захваченном трафике нашёлся
хорошо знакомый по прошлым записям артефакт: счётчик периодически, вне
зависимости от того, что происходит в HDLC/DLMS-обмене, шлёт кадр-анонс
протокола **DL/T645-2007** (`0x68 ... 0x16`, см. запись от 2026-08-18
выше — это и есть «китайский», DL/T645 буквально китайский национальный
стандарт для счётчиков). Разбор кода показал вероятный механизм именно
той картины, которую описал пользователь.

**Причина**: `callhome.DlT645FilteringSocket` фильтрует DL/T645-кадры и
одиночные keepalive-нули, но только пока активен режим "ищу начало
кадра" (`_seeking`); как только найден первый настоящий байт HDLC-кадра,
фильтрация выключается НАВСЕГДА до явного `reset_seeking()`. До этой
правки `reset_seeking()` вызывался вручную и ТОЛЬКО перед каждой
попыткой SNRM (`read_via_call_home`/`read_load_profile_via_call_home`,
`callhome.py`). После успешного SNRM/UA фильтрация оставалась
выключенной до конца TCP-соединения — если счётчик присылал очередной
DL/T645-анонс уже ПОСЛЕ установления HDLC-связи (между AARQ и AARE,
между GET и GET-response, а особенно вероятно — в паузах
многокадрового чтения профиля нагрузки, самой долгой по времени
операции из всех), эти байты шли напрямую в HDLC-парсер
(`hdlc.read_frame_from_transport`) как будто это начало следующего
кадра. Тот ждёт первым байтом строго `0x7E`; DL/T645-кадр начинается с
`0x68` — результат: либо мгновенный `GatewayError` "ожидался флаг
0x7E", либо, при менее удачном стечении границ чтения из сокета, что-то
менее определённое — то самое «не пакетами, не видно начала/конца».

**Исправление**: фильтрация теперь переигрывается автоматически перед
КАЖДЫМ кадром, а не только перед первым. `transport.TcpTransport`
получил метод `reset_frame_seeking()` (для обычного сокета — no-op; для
`DlT645FilteringSocket` — делегирует в `reset_seeking()`),
`hdlc.read_frame_from_transport` вызывает его в самом начале, перед
чтением байта-флага. Поскольку ВСЕ кадры (SNRM/UA, AARQ/AARE,
GET/GET-response, датаблоки профиля нагрузки) проходят через эту одну
функцию, фикс автоматически покрывает всю сессию целиком — ручные
вызовы `reset_seeking()` в `callhome.py` стали избыточны и убраны.

Новый тест `test_read_frame_from_transport_filters_dlt645_noise_between_frames`
(`test_callhome.py`) — читает через один `TcpServerTransport` два кадра
подряд с DL/T645-шумом МЕЖДУ ними, без явного `reset_seeking()` между
чтениями. Проверено вручную (временный откат правки), что без фикса
тест падает именно так, как предсказано: `GatewayError: Ожидался
открывающий флаг HDLC 0x7E, получено: 00` — то есть механизм
воспроизведён и объяснён кодом, даже без живого повторения на реальном
счётчике в эту сессию. Gateway: 121 -> 122 (+1). Backend/Frontend без
изменений.

**Не подтверждено на живом счётчике** — как и с фиксом порядка
scaler_unit/value выше, вся эта сессия страдала от нестабильного
call-home (тайминг окна звонка), живого чтения профиля добиться не
удалось. Правка сделана по прямой байтовой улике из захваченного
трафика (сам DL/T645-анонс, знакомый по первым сессиям проекта) и
логическому разбору кода, не по прямому наблюдению отказа при чтении
профиля.

**Частичное живое подтверждение тем же вечером**: после того как
сработавшее в 13:30 UTC ежедневное расписание забило очередь job'ов на
~3 часа, оставшиеся в очереди `read_current` (138 из них) отменены
вручную (`UPDATE jobs SET status='FAILED'` для незапущенных — оператор
подтвердил через AskUserQuestion), чтобы пропустить вперёд 5 тестовых
`read-load-profile`. Из пяти живых попыток (счётчики `201811000040`,
`201811000055`, `201901230049`, `201903000614`, `201903000617`): три не
достучались до счётчика (обычная проблема тайминга call-home, см.
раздел про массовую активацию выше) или упёрлись в `TIMEOUT` ещё на
AARE — но одна (`201811000055`) прошла ПОЛНОСТЬЮ SNRM→UA→AARQ→AARE→GET
capture_period→GET профиля, три реальных раунд-трипа подряд внутри уже
установленной сессии, и НИ РАЗУ не столкнулась с испорченным
кадром/некорректным флагом — именно тот сценарий (несколько кадров
подряд после установления связи), где раньше мог бы вклиниться
непрофильтрованный DL/T645-анонс. Сам GET профиля отклонён счётчиком
чисто на уровне протокола (`data-access-result=250`, "other-reason") —
это отдельный, не связанный с текущим багом вопрос: вероятно, OBIS
буфера профиля нагрузки (`DEFAULT_LOAD_PROFILE_OBIS`, изначально
задокументирован в `load_profile.py`/`schemas.py` как «рабочая
гипотеза», не подтверждённая реальным трафиком) не тот, что этот
конкретный счётчик поддерживает — не исследовалось дальше в рамках
этой задачи. Столкнуться с самим DL/T645-шумом посреди сессии живьём
так и не удалось (недостаточно попыток), но факт чистого разбора трёх
кадров подряд без сбоя — хоть и не прямое, но обнадёживающее
подтверждение фикса.

## Показания снова без дробного разделителя (в 1000 раз больше нужного): формула масштабирования не учитывала unit=Wh (2026-09-07)

Пользователь снова указал на пример: счётчик `202302003956` отдаёт
`6101020` вместо `6101.020`. К этому моменту порядок GET scaler_unit/
value уже исправлен (см. выше) и подтверждён живым чтением — то есть
scaler ЧИТАЕТСЯ теперь корректно, но формула его применения оказалась
неполной.

**Диагностика**: живое чтение (после приоритизации нескольких job'ов
через временную правку `created_at`, минуя очередь ежедневного опроса)
дало прямые данные с реальных счётчиков: `scaler=1` (не `-2`, как в
единственном ранее подтверждённом примере с 4507.70) для двух разных
счётчиков (`202308004436`: raw=1005950; `202308004446`: raw=132354).
Без исправления `raw_value * 10**scaler` даёт число РОВНО в 1000 раз
больше правильного и без дробной части (`1005950 -> 10059500` вместо
`10059.5`) — то есть баг не в отсутствии масштабирования (это уже
исправлено), а в том, что сама формула масштабирования неполна.

**Причина, уже задокументированная в тестах, но не реализованная в
коде**: `test_real_capture_replay.py` (тест на РЕАЛЬНОМ захваченном
трафике счётчика `202306004113` ещё от 2026-08-18!) в
`test_decode_real_scaler_unit_response` фиксирует реальный scaler_unit
`[1, 30]` (scaler=1, unit=30=Wh по Green Book), а
`test_decode_real_value_response_and_apply_scaler` — ПРАВИЛЬНУЮ формулу
для этого случая: `kwh = raw_value * (10**scaler) / 1000` (raw=66619 ->
666.19). Но этот тест вычисляет `kwh` ЛОКАЛЬНО, инлайн, только для
проверки байтового разбора GET-response — он НИКОГДА не вызывал
production-функцию `hdlc_dlms.read_register_via_established_link`,
которая применяла `raw_value * 10**scaler` БЕЗ `/1000`. Расхождение
между «формулой, задокументированной тестом» и «формулой, реально
исполняемой кодом» пролежало в проекте с 2026-08-18 незамеченным,
потому что ни один тест не проверял их совпадение.

**Исправление**: `dlms.py` — новая константа `UNIT_WATT_HOUR = 30`.
`hdlc_dlms.read_register_via_established_link` теперь читает ОБА поля
scaler_unit (`scaler`, `unit`), и при `unit == UNIT_WATT_HOUR` использует
эффективный показатель степени `scaler - 3` (перевод Вт·ч в кВт·ч,
единица, в которой везде в проекте отображается энергия — см.
OBIS.xlsx) вместо просто `scaler`. Важно: перевод нужен ДАЖЕ при
`scaler=0` (случай пользователя, `202302003956`) — старая формула в
этом случае делала ранний `return raw_value` вообще без вычислений,
что и объясняет именно этот пример. Два новых теста на реальных
захваченных числах: `test_register_read_applies_watt_hour_to_kwh_conversion`
(66619/scaler=1/unit=30 -> 666.19) и
`test_register_read_applies_watt_hour_conversion_even_with_zero_scaler`
(6101020/scaler=0/unit=30 -> 6101.02). Эмулятор (`register_units` —
новый параметр `make_hdlc_dlms_handler`/`serve_hdlc_dlms_session`)
теперь позволяет тестам задавать unit наравне со scaler (раньше unit
был всегда захардкожен в 0). Gateway: 122 -> 124 (+2). Backend/Frontend
без изменений (JSONB `value_json` одинаково хорошо хранит любое число).

**Живое подтверждение в этот же день**: после пересборки и перезапуска
`gateway-risesun` счётчик id=28 дал `raw=5091381, scaler=1, unit=30`
(эффективный показатель −2) -> `50913.81` — ровно по новой формуле,

DLMS-обмена вовсе — фикс для ЭТОГО конкретного счётчика формулой
подтверждён косвенно (тем же кодом, что и для id=28), но не отдельным
прямым чтением в эту сессию.

**Открытый вопрос**: подтверждён только один вариант unit (30, Wh) —

## Параллельные воркеры задач — очередь на одном счётчике/сек не масштабируется на рост парка (2026-09-07)

Пользователь заметил: при текущем небольшом числе call-home счётчиков
очередь job'ов уже заметно копится (см. разделы выше — минуты ожидания
на каждое ручное чтение); при росте парка в 20 раз система полностью
встанет. Спросил, можно ли читать счётчики параллельно — сначала
попросил только ответить, не делать.

**Разбор архитектуры показал: Gateway уже готова к параллелизму, узкое
место — только Backend.** `grpc_server.serve()` — синхронный gRPC-
сервер на `ThreadPoolExecutor` (`ReadRegister`/`ReadLoadProfile` —
обычные блокирующие `def`-методы, не `async`), пул call-home соединений
(`CallHomePool`) защищён `threading.Lock` на всех операциях — то есть
несколько чтений РАЗНЫХ счётчиков технически уже могли выполняться
одновременно в разных потоках пула. А вот `backend/app/services/
job_worker.worker_loop` — единственная asyncio-задача (`main.py`,
`asyncio.create_task(worker_loop(...))`, ровно один вызов), которая
берёт ОДИН job, ждёт его целиком (до 150-220с на call-home операции) и
только потом берёт следующий. Сам захват job'а (`_claim_next_job`,
`SELECT ... FOR UPDATE SKIP LOCKED`) уже написан с расчётом на
конкурентный доступ (комментарий в коде: «безопасный захват задачи при
нескольких экземплярах Backend одновременно, ТЗ п. 4.6») — просто

## Байтовая диагностика 45с ожидания AARE: полная тишина на TCP-уровне (2026-09-08)

Продолжение предыдущей секции — по просьбе пользователя сделан
`tcpdump -i any -n -tttt port 2009` на хосте (~2.5 минуты живого
трафика), сопоставлен по `conn_no`/peer с логами Gateway, разобраны
ДВА независимых TCP-потока, оба целиком попавшие в окно захвата и
оба закончившиеся штатным `AARQ/GET ... не пришёл за 45с (TIMEOUT)`
(счётчики `201811000040` через `10.86.0.161:13618` и второй через
`10.86.3.5:8128`).

**Оба потока показывают идентичную, чистую картину:**

1. TCP-handshake (`SYN`/`SYN-ACK`/`ACK`) — мгновенно, без аномалий.
2. Счётчик сам присылает 26 байт (DL/T645-анонс, съедается
   `DlT645FilteringSocket`) практически сразу после коннекта.
3. Gateway шлёт SNRM (35 байт) — ACK от счётчика приходит быстро
   (~0.1-1.3с).
4. Счётчик шлёт UA (35 байт) — HDLC-линк установлен.
5. Gateway немедленно шлёт AARQ (73 байта) — счётчик TCP-ACK'ит его за
   **80-120мс** в обоих случаях. Доставка на транспортном уровне
   подтверждена быстро и однозначно.
6. **Дальше — ровно 45.0с ПОЛНОЙ тишины с обеих сторон**: ни данных, ни
   retransmission, ни `RST`, ни keepalive, ни window update — вообще
   ничего, TCP-сессия просто "висит" молча в обе стороны.
7. Когда у Gateway истекает СВОЙ таймаут (`association_timeout_ms`),
   ОН сам шлёт `FIN` (наш `pc.raw_sock.close()`), причём с
   ретрансмиссией (счётчик не ACK'ит первые 2 попытки) — и только
   спустя **1.0-1.2с** счётчик ACK'ит `FIN` и сам корректно закрывает
   соединение встречным `FIN` (не `RST`).

**Вывод, теперь подтверждённый на байтовом уровне, а не только по
статистике**: проблема не в сети, не в NAT/операторе, не в churn
Gateway (все эти уровни отработали безупречно — доставка AARQ
подтверждена за миллисекунды, разрыв инициирует и завершает именно
Gateway своим таймаутом, а не сеть или счётчик обрывом/RST). Стек
TCP/IP счётчика жив и исправен на всём протяжении (что доказывает
корректный ответ на `FIN` В КОНЦЕ). Проблема — конкретно в
DLMS/COSEM-прикладном уровне ПРОШИВКИ счётчика: она либо обрабатывает
AARQ (проверку пароля/формирование AARE) заведомо дольше 45с, либо не
формирует ответ вовсе при каких-то условиях, которые пока не
установлены. Заметное дополнительное наблюдение: даже базовый ACK на
голый `FIN` в конце занял на порядок дольше (>1с), чем ACK на все
предыдущие пакеты (<150мс) — похоже на то, что прошивка/модем в этот
момент чем-то занят или выходит из "подвисшего" состояния.

**Не проверено в этой сессии** (следующий кандидат для диагностики):
приходит ли AARE вообще, если ждать дольше 45с (например 120-180с на
одном соединении) — то есть это "очень медленно" или "никогда". Без
этого эксперимента нельзя отличить гипотезу "прошивке просто нужно
больше времени" от "прошивка никогда не ответит на этот конкретный
AARQ" (например, из-за пароля/контекста запроса, которые формирует
Gateway). Изменений кода по итогу этой секции нет — чисто
диагностическая находка.

## Эксперимент с ожиданием AARE 150с вместо 45с: AARE так и не пришёл, но найден отдельный баг таймаута (2026-09-08)

По просьбе пользователя — точечный эксперимент вместо изменения
поведения всей системы. В `grpc_server.py` (`_do_read`) существующее,
ранее игнорировавшееся для `call_home=true` поле `timeout_ms` из
`ReadRegisterRequest` прокинуто как оверрайд `association_timeout_ms`
(при 0 — поведение не меняется, обратная совместимость сохранена).
Тесты Gateway 124/124, пересобран и передеплоен образ.

Прямым gRPC-вызовом (в обход очереди job'ов Backend, чтобы не
задевать параллельный трафик) прочитан один конкретный счётчик
(`201811000042`) с `timeout_ms=150000`. Параллельно шёл `tcpdump` на
порту 2009.

**Результат по логам Gateway** (истина только на стороне сервера —
клиентский dead line в самом эксперименте был выставлен слишком
впритык к серверному бюджету и сработал раньше, это не влияет на
серверную часть картины): `AARQ/GET на соединении #29 подтверждён TCP,
но AARE/GET-response не пришёл за 150с (TIMEOUT)`. **AARE не пришёл
даже за 150с** (в 3.3 раза дольше обычного) — гипотеза "просто нужно
чуть больше времени" тоже не подтвердилась в этом единичном прогоне.

**Но байтовый разбор pcap вскрыл отдельную, самостоятельную находку**:
между отправкой AARQ и итоговым таймаутом счётчик всё-таки прислал 3
байта `00 00 00` (дважды подряд, идентичный повтор) — это ровно та
самая keepalive-заглушка, которую `DlT645FilteringSocket` корректно
съедает как шум (см. её докстринг про одиночные нулевые байты). Эти 3
байта прилетели через ~83с после ACK на AARQ. Итоговый `FIN` от
Gateway ушёл ровно через 150.000с **от момента этих трёх байт**, а НЕ
через 150с от отправки AARQ (что было бы на ~83с раньше) — численно
проверено по pcap-таймстампам (последний из двух дублей "нулевого"
пакета в 10:18:52.750, `FIN` в 10:21:22.722, разница 149.97с).

**Причина — в `transport.py`/`callhome.py`**: `sock.settimeout(...)`
в Python не задаёт единый абсолютный дедлайн на всю операцию — это
таймаут КАЖДОГО ОТДЕЛЬНОГО блокирующего `recv()`. `TcpTransport.recv_exact()`
(`transport.py:141`) и `DlT645FilteringSocket.recv()`
(`callhome.py`) оба вызывают `self._sock.recv(...)` в цикле —
КАЖДЫЙ такой вызов получает полный таймаут заново. Значит, если во
время ожидания AARE прилетает ХОТЬ ОДИН байт (даже отфильтровываемый
как шум keepalive), таймаут-отсчёт незаметно обнуляется и начинается
заново — реальное время ожидания может быть сколь угодно больше
номинального `association_timeout_ms`, без единой строчки в логе,
которая бы это показала (лог печатает НАСТРОЕННОЕ значение, а не
фактически прошедшее время).

**Значение находки**: это отдельный от "AARE не приходит" баг —
разговор идёт не о ТОМ, отвечает ли счётчик, а о том, что наш
собственный таймаут не гарантирует то, что обещает (жёсткую верхнюю
границу ожидания). На практике это означает: часть held-соединений
и/или воркеров может задерживаться значительно дольше
`association_timeout_ms`, если по каналу проскакивает случайный шум
(что для GPRS/сотовой связи не редкость) — потенциально усугубляет
исходную проблему нехватки held-соединений под весь парк (см. секцию
про окно 10->300 выше), но с другой стороны. Похожий механизм (`recv_exact`)
используется и для чтения профиля нагрузки, где "сброс на активность"
может быть НАМЕРЕННО желаемым поведением (легитимная многосекундная

внесено — доложено пользователю, ждём решения.

10-минутку, не упало). Разрыв начался около 03:50-04:00.

**Причина №1 — свои же рестарты Gateway во время сегодняшней диагностики**
(окно 10->300 в 03:43:54, оверрайд `timeout_ms` в 04:16:50, абсолютный

уничтожает пул held-соединений целиком и обрывает уже идущие чтения на
Backend — подтверждено логами `mmws-backend-1` за 04:00-04:45: 33×
`DEADLINE_EXCEEDED`, 16× `UNAVAILABLE: Connection refused`, 16×
`UNAVAILABLE: Stream removed (Socket closed)` (в спокойный час до этого
— единицы). Плюс сам базовый процент успеха AARE и так крайне низкий
(~3-4%, см. секции выше) — ноль успехов за 30-45 минут не аномалия сама
по себе, рестарты только усугубили. Текущее (третье) состояние Gateway,
не потревоженное больше 10 минут на момент проверки, вело себя
статистически нормально (35 попыток AARQ/GET, 0 успехов — при базовой
ставке ~3% это в пределах обычной невезучей полосы, `P(0|~1)≈35%`).

**Почему вчера рост был быстрее**: до вчерашнего фикса дублей
планировщика (см. выше, «планировщик плодил дубликаты») реально
опрашивалось лишь небольшое подмножество ~10-20 счётчиков — и туда
преимущественно попадали уже вручную подтверждённые вживую «рабочие»
счётчики. После фикса планировщик честно перебирает все 141 —
включая счётчики с непроверенными/худшими условиями связи и (см. ниже)
с структурным багом адресации, которые АБСОЛЮТНО никогда не читались и
раньше — сегодняшний процент ниже на вид, но представительнее.

**Причина №2 — отдельный, не связанный с сегодняшними правками, найденный
попутно баг**: 22 счётчика (~15% парка, `SELECT ... WHERE
right(serial_number,5)::int >= 16384`, все с серийниками вида
`2019012300XX`/`20d901230XXX`/`2019f1230XXX`) валят JOB на КАЖДОЙ
попытке необработанным исключением `Компоненты адреса вне диапазона 14
бит: logical_device=1, physical_address=30004` (и т.п.) —
`WORKER_ERROR` с полным трейсбеком вместо чистого `FAILED`. Причина:
`addressing.physical_address()` берёт последние 5 СИМВОЛОВ серийника
как физический адрес (правило из `METER MANAGE USER MANUAL.docx`,
подтверждено раньше — см. секцию про 141 счётчик), но
`hdlc.server_hdlc_address()` кодирует его как raw-число в 14 бит
(лимит 16383, подтверждён реальным трафиком как ширина ОДНОГО
компонента 4-байтной HDLC-адресации DLMS/COSEM — это не Risesun-
специфичное ограничение, это стандарт). 5 десятичных цифр физически
могут доходить до 99999 (17 бит) — правило «последние 5 цифр» само по
себе несовместимо с 14-битным полем для части серийников, и это
математически неизбежно повторится для любого будущего счётчика с
последними 5 цифрами ≥ 16384, не только для этих 22. По логам Backend
баг стабильно воспроизводится с 01:45 (последний рестарт Backend,
3+ часа) — то есть существует с момента массовой активации этих
счётчиков (19 авг - 3 сен), не новый и не от сегодняшних правок.

**Проверено и отвергнуто как путь решения**: рискованно гадать новую
схему кодирования (например, брать адрес по модулю 16384 или
перераспределять избыток в `logical_device`) без подтверждения на
реальном трафике — ни один из этих 22 счётчиков ни разу не отправил ни
байта в рамках протокола (крах происходит ДО сетевого ввода-вывода),
подтвердить гипотезу нечем. Проверен `ver2.zip` (по аналогии с
секцией про 141 счётчик) на предмет исторически сохранённых реальных
физических адресов для конкретно этих 22 серийников — см. следующую
запись, если проверка дала результат.

## Fix: AddressingError вместо краха для 22 счётчиков с адресом вне 14 бит (2026-09-08)

`errors.py` — новый класс `AddressingError(GatewayError)`, код
`ADDRESSING_ERROR`. `hdlc.server_hdlc_address()` теперь поднимает его
вместо голого `ValueError` (см. предыдущую секцию про находку бага) —
`GatewayError`/подклассы уже перехватываются везде выше по стеку
(`callhome.py` retry-циклы, `grpc_server.ReadRegister`), а голый
`ValueError` — нет, поэтому и падало необработанным исключением
(`WORKER_ERROR` с полным трейсбеком в Backend).

Дополнительно — `callhome.read_via_call_home` и
`read_load_profile_via_call_home` теперь проверяют адресуемость serial
ДО входа в цикл ожидания held-соединения, а не только внутри
`establish_link()` на первой попытке SNRM: без этого джоб держал бы
воркер и потенциальное held-соединение занятыми весь `max_wait_s` (до
150с) на заведомо детерминированно обречённую попытку — теперь падает
за миллисекунды, до сетевого ввода-вывода.

Тесты: Gateway 124 -> 126 (+2:
`test_server_hdlc_address_rejects_5_digit_overflow` переведён с
`pytest.raises(ValueError)` на `AddressingError`,
`test_read_via_call_home_fails_fast_on_unaddressable_serial` — новый,
проверяет и тип ошибки, и что укладывается в <1с при `max_wait_s=30`).

**Живое подтверждение** прямым gRPC-вызовом (`serial=201901230004`,
один из 22) после передеплоя: ответ за **0.003с** — чистый
`ADDRESSING_ERROR` вместо зависания на 150с и краха с трейсбеком.

**Что осталось нерешённым осознанно**: сами эти 22 счётчика по-прежнему
НЕ читаются — фикс не угадывает правильную схему кодирования (см.
предыдущую секцию, почему это признано неоправданным риском без
реального трафика), только останавливает бесполезную трату ресурсов
и мусор в логах. Правило «последние 5 цифр серийного» из заводского
руководства математически несовместимо с 14-битным полем для любого
серийника с последними 5 цифрами ≥ 16384 — это будет повторяться и
для будущих счётчиков с таким же паттерном серийника, не только для
текущих 22. Настоящее решение требует либо доступа к реальному одному
из этих счётчиков (byte-level подтверждение правильной адресации по
аналогии со всеми прошлыми находками в этом файле), либо официальной
документации протокола от Risesun/CHINT для этого диапазона
серийников, которой пока нет.

**Подтверждение через реальный (не ручной) цикл планировщика**: спустя
~10 минут после деплоя штатный джоб для счётчика `20d901230058` (один
из 22, поставлен в очередь планировщиком, не мной вручную) сам дошёл
до выполнения и корректно завершился `FAILED` с `error->>'code' =
'ADDRESSING_ERROR'` — без единого нового трейсбека «вне диапазона 14
бит» в логах Backend с момента деплоя. Замеченные в те же минуты ~40
`DEADLINE_EXCEEDED`/`UNAVAILABLE` в логах Backend — это самим же этим
рестартом Gateway вызванный кратковременный «холодный старт» пула (тот
же механизм, что и в секции «свои же рестарты» выше), не новая
проблема; за 90 секунд без новых рестартов частота уже спадает.

## Настоящая схема адресации для партии 201901230001..201901230186 — от завода (2026-09-08)

Пользователь сообщил точный алгоритм от завода для партии счётчиков
201901230001..201901230186 (ровно те самые 22, что валили
`AddressingError` — см. секции выше): физический адрес = последние 4
цифры серийного + 199, а НЕ последние 5 цифр целиком. Пример от
завода: `201901230001` -> `00001 + 199` = `00200`. Устраняет
переполнение 14-битного поля математически — для всего диапазона
результат лежит в 200..385 (последние-4-цифры от 1 до 186 плюс 199),
комфортно внутри 16383, в отличие от старого правила, дававшего
30001..30186.

**Правка**: `addressing.physical_address()` — для серийников,
попадающих в этот числовой диапазон (`serial.isdigit()` и
`201901230001 <= int(serial) <= 201901230186`), физический адрес
считается по новой формуле; для всех остальных серийников (включая
соседние `201901230000`/`201901230187`) правило "последние 5 цифр"
не изменилось. Режим C (использует серийный номер целиком) правилом
партии не затрагивается.

Тесты: Gateway 126 -> 130 (+4: пример завода `00200`, верхняя граница
диапазона `00385`, соседи диапазона вне спецправила, MODE C не
затронут). Пересобран и передеплоен.

**Живое подтверждение**: прямой gRPC-вызов на `201901230004` (один из
22) — раньше падал за 0.003с с `ADDRESSING_ERROR`, теперь честно ждёт
(упёрлись в клиентский таймаут 20с, `DEADLINE_EXCEEDED` — счётчик
сейчас физически не подключён, это ожидаемо, не ошибка). Отсутствие
мгновенного `ADDRESSING_ERROR` подтверждает, что адрес теперь
проходит валидацию как у любого нормального счётчика. Полноценное
подтверждение чтением ждёт, пока кто-то из этой партии реально
позвонит домой.

## Счётчик "Online" на дашборде уходил на убывание — таймаут online поднят с 1ч до 24ч (2026-09-08)

Пользователь заметил: счётчик "Online" на дашборде идёт на убывание.
Проверка `/api/dashboard`: meters_online=27, meters_offline=120 из 147.

Разбор `Meter.is_online` (backend/app/models.py): счётчик считается online,
если `last_seen_at` обновлялся в пределах `meter_offline_timeout_s` (было
3600с = 1ч) ИЛИ было успешное чтение сегодня по местному календарю.
`last_seen_at`/`last_read_at` обновляются ТОЛЬКО при успешном чтении
(job_worker.py, ветка `if outcome.ok:`) — не на самой попытке связи.

Причина не в баге планировщика, а в арифметике объёма после сегодняшнего
перехода на профиль опроса по умолчанию из 18 OBIS-кодов (см. запись про
профили опроса выше): число пар "счётчик×код" выросло со 147 (1 код на
счётчик) до 2646 (18×147), а суммарная пропускная способность воркеров не
изменилась (8 воркеров, ~3 попытки/мин ≈ 192 попытки/ч). Полный круг по
очереди стал занимать не ~45 минут, а ~14 часов. При том же ~4% успехе на
попытку ожидаемое число счётчиков с успешным чтением за час упало
пропорционально росту профиля — расчёт (~7.6/ч) почти точно совпал с
наблюдаемым (9/ч за последний час на момент проверки). То есть счётчики не
теряли связь — до них физически не успевали дойти в очереди за старое
часовое окно "online".

Решение: `meter_offline_timeout_s` в backend/app/config.py поднят с 3600
до 86400 (24 часа) — согласовано с пользователем через явный выбор (24ч
из предложенных вариантов). Значение синхронизировано с тем, что профиль
опроса по умолчанию сам задуман как ежедневный ("каждый день, пока не
отключат"). Живое подтверждение после передеплоя backend: с новым порогом
online = 107 из 147 (было 27) — те же самые счётчики, которые реально
отвечают на текущей скорости опроса, теперь корректно распознаются как
находящиеся на связи.

Переменных окружения, переопределяющих `meter_offline_timeout_s`, в
docker-compose.yml/.env не найдено — значение из кода является
единственным источником.

- Frontend: `MetersListPage.tsx` — секция "Некорректные данные" с

## 12 часов без единого успешного чтения — самоусиливающийся затор очереди (2026-09-09)

Пользователь: «за 14 часов ни одного удачного чтения, выясни причину». Проверка
подтвердила: последнее SUCCEEDED — 2026-09-08 14:00:22 UTC, дальше 11031 FAILED
подряд без единого успеха (~12 часов). Вероятность такой серии при обычных
~1-4% success rate практически нулевая — явный признак реальной поломки, а не
невезения.

**Найденный механизм (самоусиливающийся коллапс очереди)**:
- Расписание id=6 («Опрос по умолчанию (obis1.xlsx) — весь парк») стояло на
  `*/30 * * * *` — каждые 30 минут, а не «раз в день», как явно просил
  пользователь при постановке задачи («Опрос по умолчанию должен работать
  каждый день, пока его не отключат») — это моя собственная ошибка при
  реализации, cron не соответствовал сказанному.
- `_trigger_one` на каждый тик ставит в очередь по одной Job на каждый ещё НЕ
  прочитанный сегодня OBIS профиля для каждого счётчика без текущей
  невыполненной задачи (`skip_if_read_today`). При обычном success rate это
  безопасно — большинство пар со временем помечаются «прочитано сегодня» и
  выпадают из повторной постановки. Но при близком к нулю success rate
  ПОЧТИ НИЧЕГО не помечается прочитанным — то есть каждые 30 минут для любого
  освободившегося счётчика заново встаёт в очередь чуть ли не весь его
  профиль (до 22 OBIS).
- Пропускная способность системы жёстко ограничена (8 воркеров × ~150с на
  попытку ≈ 194 попытки/час максимум), а полный цикл профиля — 147×22≈3234
  пары. Пока очередь маленькая, соединения к моменту попытки ещё свежие
  (`CallHomePool.claim(max_age_s=30s)` — только что принятые), success rate
  в норме. Как только очередь начинает расти быстрее, чем воркеры успевают
  её разбирать, время от постановки job'а до реальной попытки растёт — и
  соединение к этому моменту почти гарантированно уже вытеснено/протухло
  (старше 30с), попытка проваливается. Больше провалов -> быстрее
  освобождаются "невыполненные задачи" -> чаще срабатывает
  `skip_if_read_today`-fallback повторной постановки -> очередь растёт ещё
  быстрее. Замкнутый круг, из которого система сама выйти не может.
- **Прямое подтверждение**: очередь (QUEUED) за ночь ВЫРОСЛА с 1175 (22:20) до
  1894 (07:47), хотя воркеры не останавливались (FAILED +1819 за то же
  время) — то есть новых job'ов создавалось ~267/час при максимум ~194/час
  пропускной способности.

**Фикс**: `cron_expression` расписания id=6 изменён с `*/30 * * * *` на
`5 18 * * *` (00:05 по Бишкеку, раз в сутки) — прямой SQL UPDATE
(`scheduled_jobs`), без изменения кода: сам механизм `_trigger_one`/
`skip_if_read_today` корректен и рассчитан именно на разовый ежедневный
триггер, просто cron изначально был выставлен неверно. Один тик в сутки
ставит весь профиль (~3234 пары) один раз, дальше 24 часа на его разбор
воркерами — с большим запасом по сравнению с пропускной способностью
(194×24=4656/сутки), без повторного самонакручивания. Существующий бэклог
(1894 QUEUED на момент фикса) чинить/чистить не стал — он сам растает за
несколько часов, раз новые партии больше не подсыпаются каждые полчаса.

Урок на будущее: при реализации «запускать раз в день» задачи в этом
планировщике — явно проверять итоговый `cron_expression` в БД, а не
полагаться на то, что где-то в коде "по умолчанию" стоит подходящий интервал
опроса (`*/30 * * * *` был унаследован от более ранней, тестовой версии
этого же расписания, см. запись «ТЕСТ: По умолчанию (obis1.xlsx)» с тем же
интервалом, id=5).

## Событийное чтение call-home сразу при подключении — архитектурная переделка (2026-09-09)

Продолжение вчерашнего кризиса (0 успехов ~12 часов). Пользователь предоставил
рабочую референсную реализацию — легаси C#/.NET-программа (`MMSCA.MT`, на базе
библиотеки Gurux.DLMS), которая "более-менее справлялась с задачей". Разбор
`Program.cs`/`GXDLMSReader.cs` вскрыл принципиальную архитектурную разницу с
нашей системой:

- **Их подход**: `OnClientConnected` — в момент подключения счётчика —
  немедленно, в отдельном потоке, на ТОЛЬКО ЧТО принятом соединении делает
  весь обмен SNRM→AARQ→AARE→чтение. Короткие таймауты (5с×3 попытки), потому
  что соединению всегда ноль секунд от роду — не нужно закладываться на
  протухание. Читает ВСЕ нужные объекты за одну ассоциацию
  (`ExecuteMeterTasks`), не по одному на каждый.
- **Наш подход (до этого фикса)**: `CallHomePool` принимает соединение,
  кладёт его в пул "на потом". Реальная попытка SNRM/AARQ происходит только
  когда Backend'овский FIFO-воркер (`SELECT...FOR UPDATE SKIP LOCKED ORDER BY
  created_at`) доберётся до конкретного job'а — при заметном бэклоге (тысячи
  job'ов, ~18-22 OBIS на счётчик) это может быть от секунд до ЧАСОВ после
  того, как соединение было принято — систематически ПОСЛЕ истечения "окна
  жизни" соединения (~30-60с, подтверждено байтовым tcpdump 2026-08-18 и
  повторно 2026-09-09).

Полный план — `/root/.claude/plans/ticklish-popping-bear.md`. Реализовано:

**Backend** (`app/config.py`, `app/auth/gateway_internal_deps.py`,
`app/schemas.py`, `app/api/gateway_internal.py`, `app/services/job_worker.py`,
`app/main.py`) — два новых внутренних HTTP-эндпоинта
(`POST /api/internal/gateway/meters/{serial}/claim-jobs`,
`POST /api/internal/gateway/job-results`), авторизация общим секретом
(`X-Internal-Secret`, `secrets.compare_digest`), не пользовательская JWT.
`claim-jobs` атомарно (`FOR UPDATE SKIP LOCKED`, новая
`claim_due_jobs_for_meter`) забирает due job'ы конкретного счётчика,
переводит в RUNNING, отдаёт расшифрованный пароль. `job-results` финализирует
их через вынесенные `finalize_read_current_job`/`finalize_read_rated_current_job`
(тот же код, что и у старого воркера — чистый рефакторинг, поведение старого
пути не изменилось) — но ТОЛЬКО если job всё ещё RUNNING (анти-задвоение).
Новый `stale_job_reaper_loop` (раз в 60с, порог 300с) возвращает в QUEUED
job'ы, которые Gateway забрал, но не смог отчитать (сеть/сбой) — страховка.
Глобальный выключатель `immediate_read_enabled` (по умолчанию **False**) +
`immediate_read_allowed_serials` для поэтапного раскатывания.

**Gateway** (`backend_client.py` — новый, на `urllib` без новых зависимостей;
`protocols/hdlc_dlms.py` — `read_registers_via_established_link`, одна
ассоциация на несколько OBIS вместо одной на каждый; `callhome.py` —
`read_batch_via_fresh_connection` + `CallHomePool._maybe_trigger_immediate_read`,
вызывается из `_identify()` сразу после опознания серийника) — оба HTTP-вызова
к Backend fail-closed (сеть недоступна/секрет не задан → `None`/`False`,
соединение остаётся в пуле нетронутым для старого пути — новый путь
дополняет, не заменяет).

**По просьбе пользователя, важный нюанс**: как только одно соединение
счётчика становится активным (событийный путь его забрал), ВСЕ ОСТАЛЬНЫЕ
held-соединения ТОГО ЖЕ счётчика в пуле закрываются сразу же — реализовано в
`_maybe_trigger_immediate_read`. Держать несколько параллельных TCP-сессий к
одному счётчику без ответа ни по одной может само по себе путать
модем/прошивку. Второй пункт (HDLC keepalive на активном соединении для
переиспользования ассоциации без повторного SNRM+AARQ) — сознательно НЕ
реализован в этом заходе, отмечен в плане как требующий отдельной байтовой
проверки (неизвестно, действительно ли периодический HDLC RR продлевает
жизнь соединения, а не просто полное бездействие).

**Найденная и исправленная в процессе ошибка собственного дизайна**:
`GatewayError`-подклассы `ConnectionLostError`/`MeterTimeoutError`
(транспортный уровень, БРОСАЮТСЯ, а не возвращаются) изначально не
перехватывались отдельно от builtin `ConnectionError`/`OSError` в цикле
`read_registers_via_established_link` — обрыв соединения посреди батча
пошёл бы по ветке "GatewayError -> продолжить со следующим OBIS" вместо
"прервать и вернуть частичный результат", что рассинхронизировало бы
дальнейшие попытки на том же (уже мёртвом) соединении. Исправлено до
написания тестов; тест на частичный успех при обрыве
(`test_read_registers_connection_drop_mid_batch_returns_partial_results`)
специально проверяет именно эту ветку.

**Тесты**: Backend 150 (было 137), Gateway 147 (было 132) — все зелёные.
Новые: `test_gateway_internal_api.py` (авторизация, атомарность claim,
анти-задвоение job-results), `job_worker` — `claim_due_jobs_for_meter`/
`requeue_stale_running_jobs`; `test_integration_hdlc_dlms.py` —
`read_registers_via_established_link` (батч, data-access-error не топит
батч, неверный пароль падает до первого GET, обрыв — частичный результат);
`test_backend_client.py` (новый файл, настоящий `http.server`, не мок сети);
`test_callhome.py` — `_maybe_trigger_immediate_read` (Backend недоступен —
pc остаётся в пуле; job'ы есть — pc забран и отчитан; соседние
held-соединения того же счётчика закрываются).

**Раскатано "втёмную"** (`immediate_read_enabled=False`, дефолт) — оба
контейнера пересобраны и передеплоены, живое подтверждение по логам: Gateway
реально дозванивается до нового эндпоинта на каждое опознанное соединение
(до `Application startup complete` у Backend — пара запросов ожидаемо
получила `Connection refused`, ровно тот fail-closed путь, который и должен
сработать), Backend отвечает 200 OK, старый путь (воркеры, очередь) работает
без изменений (SUCCEEDED продолжает расти). Включение
(`immediate_read_enabled=true` + `immediate_read_allowed_serials` на 1-2
счётчика для канарейки) — по решению пользователя, не сделано в этом заходе.

## Проверка гипотезы про несовпадение уровня аутентификации (LLS vs HLS) — не подтвердилась (2026-09-09)

По просьбе пользователя поискано в интернете, сталкивались ли другие с
похожим симптомом (AARQ доставлен, AARE не приходит). Нашлась релевантная
зацепка на форуме Gurux: несовпадение уровня аутентификации (счётчик
настроен на HLS/HLS-GMAC, клиент шлёт LLS) — счётчик может молча
игнорировать такой AARQ вместо явного отказа. Показательно, что в
референсной C#-программе пользователя (`GXDLMSReader`) уровень
аутентификации читается ИНДИВИДУАЛЬНО по каждому счётчику из БД
(`Authentication authentication = (Authentication) int32_3`), а не
задан одним фиксированным значением на весь парк, как у нас
(`dlms.build_aarq` всегда строит LLS).

Заодно, копая эту зацепку, нашлась независимая статистическая находка в
своих же данных: код `1.1.1.8.0.ff` (исходный, с Этапа 1) даёт 2.61%
успеха (117/4483), а 8 из 17 новых кодов профиля опроса дают ровно 0%
на 300-425 попытках каждый — статистически невозможное совпадение при
одинаковой истинной вероятности. НО разбивка ошибок для этих кодов не
показывает НИ ОДНОГО случая «AARE прошло, GET отказал» (только
TIMEOUT/GATEWAY_ERROR/WORKER_ERROR — то есть отказ на уровне
соединения) — значит объяснение не «неверный OBIS», уверенного вывода
не сделано, зафиксировано как открытый вопрос.

**Реализована диагностическая возможность** (аналог `timeout_ms`
оверрайда, добавленного 2026-09-08) — `mechanism_id` в
`ReadRegisterRequest` (поле 11 в proto), прокинуто через весь путь
(`gateway_client.read_register` -> `grpc_server._do_read` ->
`read_via_call_home` -> `read_register_via_established_link` ->
`dlms.build_aarq(password, mechanism_id=...)`). 0 (по умолчанию)
сохраняет прежнее поведение (LLS) без изменений — существующие тесты
(Gateway 147, Backend 150) прошли без изменений в количестве.
`build_aarq` меняет только OID mechanism-name на
`2.16.756.5.8.2.<mechanism_id>`, тело AARQ (calling-authentication-value)
всё равно остаётся в LLS-формате (сырой пароль) — для настоящего HLS
это протокольно некорректно (там ожидается вызов-ответ), так что это
ЧАСТИЧНАЯ проверка (реагирует ли счётчик на смену заявленного
механизма вообще), не полноценное HLS-рукопожатие.

**Живая проверка**: 3 попытки на разных "всегда молчащих" счётчиках
(0 успехов за 100+ попыток каждый) — mechanism_id=2 (HLS) на
`202308004369` и mechanism_id=5 (HLS-GMAC) на `202308004182` дали тот
же TIMEOUT, что и обычный LLS (третья попытка, `202211003777`,
не поймала живое соединение вовсе — не в счёт). **Вывод**: гипотеза
ослаблена (смена заявленного механизма ничего не изменила на 2 из 2
содержательных попыток), но не опровергнута полностью — настоящая
проверка потребовала бы корректно оформленного HLS AARQ (другая
структура calling-authentication-value), не сделано в этом заходе.

Побочно найдена и исправлена несвязанная проблема при пересборке
gRPC-стабов: `backend/requirements.txt` жёстко фиксирует

## Событийное чтение живьём на всём парке: 0 успехов из 380 попыток за 24ч — гонка со временем исключена как причина (2026-09-09)

Проверка боем нового событийного пути (включён на весь парк,
`immediate_read_allowed_serials=[]`, читает СРАЗУ на свежепринятом
соединении, без очереди). За последние 24ч: 380 попыток обмена,
**0 успехов**, `POST /job-results` от Gateway ни разу не вызван за
последний час. Последний вообще успешный job во всей системе —
id=15678, 03:41:42 UTC — сухая полоса перевалила за 4ч47м на момент
проверки и продолжает расти.

Важный отдельный факт: SNRM/UA (уровень линии, ДО AARQ) на этих же
свежих соединениях проходит нормально в ~74% случаев (459 успешных
против 164 таймаутов за 2ч) — то есть счётчики физически на связи,
откликаются на линейном уровне. Останавливается всё именно на
AARQ→AARE, и останавливается теперь уже на соединениях нулевого
возраста, прочитанных мгновенно после коннекта.

**Это исключает "гонку со временем" (протухание held-соединения,
пока FIFO-очередь до него доберётся) как объяснение — раньше это было
главной рабочей гипотезой и главным обоснованием всей архитектуры
событийного чтения.** Теперь задержки нет вообще, а результат тот же
самый ноль. Значит причина не в нашей очереди/архитектуре, а
где-то на стороне счётчика/сети между AARQ и AARE — усиливает (не
опровергает) версию, уже отправленную Eric на разбор. Система при
этом подтверждённо здорова: очередь не затоплена (4 QUEUED, 17
RUNNING моложе 4 минут на момент проверки), CPU/память контейнеров в
норме, приток соединений на Gateway обычный (~194/5мин) — сухая
полоса не объясняется перегрузкой.

## Старый FIFO-путь насмерть хоронил job'ы, для которых событийное чтение ещё не успело позвонить (2026-09-10)

По просьбе пользователя перепроверил, почему за сутки «прямо совсем
ноль» — и нашёл реальный, отдельный от AARE-тишины баг. Сравнил коды
ошибок ДО сухой полосы и ВО ВРЕМЯ неё: раньше доминировал честный
`TIMEOUT` (2377 за сутки) — соединение было, AARQ ушёл, AARE не
пришло. Во время сухой полосы `TIMEOUT` упал до 81, а на первое место
вышла `GATEWAY_ERROR` с текстом «счётчик ещё не установил ни одного
call-home соединения» — 1229 из 1247 (98.5% всех `GATEWAY_ERROR`,
83% вообще всех FAILED за это время). Это НЕ AARE-тишина — job даже
не долетал до провода.

Механизм: старый FIFO-воркер (`job_worker.py`, несколько параллельных
экземпляров) всё ещё живёт рядом с событийным чтением и опрашивает
общую очередь. Событийное чтение (`_maybe_trigger_immediate_read`)
хватает и (при необходимости) закрывает любое свежее held-соединение
счётчика в момент опознания — а раз оно теперь включено на весь парк,
пул для конкретного счётчика почти всегда пуст к тому моменту, когда
до этого же job'а по FIFO доберётся старый путь. Он честно ждёт 150с
(видно по `finished_at - started_at`, у всех таких job ровно
`00:02:30`), не находит СОВСЕМ НИЧЕГО и **терминально проваливает
job** — хотя счётчик жив и просто ещё не позвонил, а через 2-4 минуты
позвонит и достанется событийному чтению, у которого был бы реальный
шанс. То есть новая архитектура невольно подставляет старую: сама
идея «дополняем, а не заменяем» обернулась тем, что старый путь стал
чистым вредом для call-home счётчиков — только съедает валидные
шансы раньше срока.

**Исправлено**: `GatewayError` для этого конкретного случая вынесен
в отдельный класс `NoConnectionEstablishedError`
(`gateway/src/mmws_gateway/errors.py`, `code="NO_CONNECTION_YET"`,
использован в обоих местах `callhome.py`, где раньше был общий
`GatewayError` с этим текстом — `read_via_call_home` и
`read_load_profile_via_call_home`). На Backend'е
(`finalize_read_current_job`/`finalize_read_rated_current_job`,
job_worker.py) этот код теперь не хоронит job, а возвращает его в
`QUEUED` (`started_at=None`, `finished_at` не трогается — job не
завершён) вместо `FAILED` — следующий звонок счётчика достанется
событийному чтению, как и задумано архитектурой. Остальные типы
ошибок (`TIMEOUT`, честный `data-access-result`, обрыв связи и т.д.)
по-прежнему заканчиваются терминальным `FAILED`, поведение не
менялось.

Тесты: Gateway 147/147, Backend 150/150 — без изменений в количестве
(это чистое добавление кода поведения, существующие тесты не
затрагивают новую ветку). Пересобрано и передеплоено (`backend`,
`gateway-risesun`), оба контейнера стартовали чисто, `claim-jobs`
отвечает 200 сразу после рестарта, fronted-прокси на backend не
сломался (известная прошлая проблема с кешем IP в nginx — не
повторилась).

**Важная оговорка**: это НЕ объясняет саму AARE-тишину (она
подтверждена независимо, даже на честных мгновенных попытках,
0 успехов из 380) — это отдельный, самостоятельный баг, который
искажал статистику и выбрасывал часть валидных шансов. Ожидаемый
эффект: доля `TIMEOUT`/`NO_CONNECTION_YET` в новых FAILED должна
измениться (меньше зря потраченных job'ов), но 0% успеха по факту,
скорее всего, никуда не денется, пока не решится основная загадка.

## Изучили, каким методом получены ВСЕ исторические успехи — событийное чтение пробует только одно соединение, старый путь — до 10 (2026-09-10)

По просьбе пользователя разобрали timing всех 154 успешных job за всю
историю проекта. Вывод однозначный: **ни один** успех не пришёл через
событийное чтение (immediate-read, включённое на весь парк уже сутки к
этому моменту и сделавшее 380+ мгновенных попыток с нулевым
результатом) — все 154 пришли через старый FIFO-путь
(`job_worker` → `read_via_call_home`). Признак виден прямо в
`created_at`/`started_at`/`finished_at`: у старого пути большой разрыв
между созданием и стартом (воркер добирается по очереди), а
`finished_at - started_at` укладывается в 6–150с — это бюджет старого
пути (`max_wait_s=150`).

Ключевое структурное отличие: старый путь (`read_via_call_home`)
перебирает ДО 10 разных held-соединений одного счётчика подряд
(`DEFAULT_MAX_PER_SERIAL=10`), пока не истечёт общий 150-секундный
бюджет — лог "AARE не пришёл — переходим к следующему соединению".
Событийное чтение до сих пор работало иначе: хватало только САМОЕ
свежее опознанное соединение и тут же закрывало ВСЕ остальные
held-соединения того же счётчика — то есть у него был всего один
"бросок кубика" вместо десяти. Похоже, именно широта перебора (а не
скорость реакции) была источником тех ~1-3% успеха, что вообще были.

**Исправлено** (`gateway/src/mmws_gateway/callhome.py`,
`_maybe_trigger_immediate_read`): вместо немедленного закрытия соседних
held-соединений того же счётчика они теперь складываются в список
кандидатов (сначала pc — только что опознанное, затем остальные от
свежего к старому, тот же принцип, что и в `claim()`) и пробуются по
очереди в общем бюджете `DEFAULT_IMMEDIATE_READ_MAX_WAIT_S=150.0`
(то же значение, что и у старого пути) — при неудаче на одном
кандидате сразу пробуется следующий, вместо того чтобы сдаваться и
ждать возврата job'ы в очередь по таймауту. Добавлен юнит-тест
(`test_maybe_trigger_immediate_read_falls_back_to_next_connection_on_failure`),
явно проверяющий сам механизм fallback (первое соединение проваливается
GatewayError, второе успешно — результат берётся со второго).

Gateway 148/148 (147 было + 1 новый тест). Пересобрано и передеплоено,
контейнер стартовал чисто. Живого подтверждения многосвязного fallback
пока нет (пул только что пуст после рестарта — соседи ещё не успели
накопиться), логика подтверждена юнит-тестом; будем наблюдать за живым
трафиком по мере наполнения пула.

## Ответ производителя (Eric, 2026-09-10) — и по нему реализована переотправка AARQ

Пришёл содержательный ответ на письмо, отправленное ранее (см.

## IPsec-туннель до Megacom (SIM-диапазон 10.86.0.0/17) — найден и закрыт пробел с DPD (2026-09-10)

По просьбе пользователя проверен MikroTik (`JAMain`, WAN
213.145.145.94, SSH-доступ), через который идёт IPsec-туннель до
Megacom — оператора, чьи SIM-карты стоят в счётчиках (диапазон
`10.86.0.0/17`, тот самый, что видим как peer-адрес в call-home
подключениях на Gateway).

Находки:
- Туннель Megacom (`profile_Megacom`) рекеится каждые ~24-30 минут
  (по логу IPsec на роутере) — заметно чаще прочих туннелей на этом же
  роутере (Beeline держится часами, Infocom — раз в 45мин-час), хотя
  настроенный `lifetime=1d1h` предполагает гораздо более редкий рекей
  — похоже, встречную частоту форсирует сторона Megacom.
- **У `profile_Megacom` был выключен Dead Peer Detection**
  (`dpd-interval=disable-dpd`), в отличие от большинства других,
  видимо более стабильных туннелей на этом роутере (`default`,
  `Cisco-KERC-new`, `NESK_JPES_Phase1`, `profile-infocom` — у всех
  `dpd-interval=2m dpd-maximum-failures=5`). Без DPD роутер не
  замечает, если Megacom реально пропадает МЕЖДУ плановыми рекеями —
  трафик может молча улетать в мёртвую SA до следующего планового
  рекея. Потенциально ровно тот класс симптома ("TCP вроде
  подтверждается, а дальше тишина"), который разбирается в этом
  проекте уже который день.
- Дважды в логе видна коллизия: обе стороны инициируют rekey
  практически одновременно (09:13:15-16, 10:37:17) — DPD это не

  Megacom, вне нашего доступа.

## IPsec-туннель Infocom — рассинхрон phase1/phase2 lifetime, не про наш проект счётчиков, но пользователь попросил заодно (2026-09-10)

Отдельная просьба пользователя (не про счётчики) — на том же роутере
пользователи периодически теряют доступ к ресурсу через туннель
Infocom, помогает только ручное «убийство» активного пира. Нашлась
причина: `profile-infocom` (phase1/IKE) — `lifetime=1h`, DPD включён
(2м/5 попыток), но `proposal-Infocom` (phase2/ESP, сама SA с
данными) — `lifetime=1d`, то есть данные-SA обновляется раз в сутки.
DPD проверяет только живость phase1 — если phase2 застревает
(рассинхрон счётчиков/коллизия рекея), IKE продолжает отвечать на
DPD, а трафик не идёт, пока не подоспеет плановый рекей почти через
сутки — отсюда и нужда убивать пир руками. Разрыв в 24 раза между
phase1 и phase2 lifetime — нетипичная, "перевёрнутая" конфигурация.

**Исправлено** (с подтверждением пользователя после блокировки
auto-mode классификатором на первой попытке): `proposal-Infocom`
lifetime сокращён с `1d` до `1h`, выровнен с phase1. Теперь даже
застрявшая phase2-SA сама переустановится в течение часа, а не
суток. Туннель пережил изменение штатно (`state=established`,
`ph2-total=2`, сразу после).

## Байтовая трассировка живой переотправки AARQ — загадка сужена до прикладного уровня прошивки (2026-09-10)

Пользователь отметил, что за 3 часа с деплоя трёх сегодняшних фиксов
(fallback на несколько соединений, переотправка AARQ, DPD на
Megacom) — ни одного успеха, ни одного случая, когда AARE реально
пришло (561 переотправок AARQ, 52 fallback — 0 результата). Взял
байтовый захват (tcpdump) одной полной сессии на счётчике
201908001878 (10.86.2.226) во время реальной переотправки AARQ,
разобрал через собственный `HdlcFrame.decode()`.

Точная картина (45 секунд, 1 исходный AARQ + 4 переотправки по 10с):
на САМЫЙ ПЕРВЫЙ AARQ нет вообще никакого HDLC-ответа — только TCP
ACK. А начиная со ВТОРОЙ попытки (первой переотправки) счётчик/модем
начинает отвечать явным HDLC-кадром **RR** (control=0x31, N(R)=1) —
и все 4 RR-ответа байт-в-байт идентичны, что является штатным
поведением HDLC-получателя на ПОВТОР уже принятого кадра (тот же
N(S)=0 при каждой переотправке). AARE не пришло ни разу за все 5
попыток.

**Вывод**: это НЕ повторяет уже известную находку про "00 00 00"
(та была неструктурированным шумом от модема) — это валидный,
корректно сформированный HDLC-кадр, подтверждающий, что удалённая
сторона: (а) точно получила самый первый AARQ (иначе не могла бы
распознать повторы как дубликаты того же N(S)), (б) активно
отслеживает состояние этой попытки ассоциации минимум 40+ секунд, но
(в) ни разу не завершает DLMS-уровень ответом (ни AARE-успех, ни
явный отказ). Это исключает потерю пакета, проблему с нашей
переотправкой и грубо некорректный AARQ (такой был бы либо
проигнорирован полностью, либо явно отклонён) — разрыв строго внутри
прикладной DLMS/COSEM-логики прошивки счётчика, между "приняли
AARQ" и "сформировали AARE".

Оформлено уточняющее письмо Eric'у (`AARE_narrowed_down.docx`,
отправлено пользователю) с этой точной байтовой трассировкой и
прямым вопросом инженеру прошивки — на что именно счётчик "ждёт"
между приёмом AARQ и генерацией AARE.
