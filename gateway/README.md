# MMWS Protocol Gateway — PoC Этапа 0

Минимальный CLI-процесс, подтверждающий возможность чтения показаний со
счётчиков Risesun по трём протокольным профилям (ТЗ п. 4.3.2):
IEC 62056-21 режим C, IEC 62056-21 режим E, HDLC + DLMS/COSEM.

Соответствует Этапу 0 согласно `../Promt_MMWS.md` (раздел «Этап 0»): без
gRPC, без базы данных, без пользователей/ролей — только протокольный слой.

## ⚠️ Программные эмуляторы vs реальное оборудование

Пакет `mmws_gateway.emulators` содержит **программные эмуляторы**
счётчика (по одному на каждый протокольный профиль), используемые
только интеграционными тестами (`tests/test_integration_*.py`) и
локальной отладкой CLI. **Это не замена проверке на реальном
оборудовании.** Определение завершения Этапа 0 (`Promt_MMWS.md`)
требует подтверждённого успешного чтения хотя бы с одного реального
счётчика/эмулятора каждого профиля — на момент написания этого файла
проверка выполнена только против собственных эмуляторов; проверка на
реальных счётчиках Risesun — обязательный следующий шаг перед закрытием
Этапа 0.

## Установка

```bash
cd gateway
pip install --user -e .          # прод-зависимости отсутствуют (stdlib)
pip install --user -e '.[test]'  # + pytest для тестов
```

## Использование

```bash
export MMWS_METER_PASSWORD='пароль_доступа'   # не для профиля mode_c
gateway read --profile hdlc_dlms \
    --host 192.168.1.50 --port 4059 \
    --serial 202006003607 \
    --obis 1.1.1.8.0.ff \
    --timeout-ms 5000 --retries 3
```

- `--profile`: `mode_c` | `mode_e` | `hdlc_dlms`.
- `--obis`: 6-байтная hex-нотация `A.B.C.D.E.F` (как в словаре OBIS,
  например `1.1.1.8.0.ff` — суммарная активная энергия приёма). Для
  `mode_c` Gateway автоматически приводит код к короткой десятичной
  нотации data readout (см. `mmws_gateway.protocols.mode_c.obis6_to_short_code`
  и оговорку в отчёте Этапа 0 — соответствие не подтверждено на
  реальном оборудовании).
- `--password`: только для `mode_e`/`hdlc_dlms`. Пароль **никогда** не
  имеет дефолта и не логируется; предпочтительный способ передачи —
  переменная окружения `MMWS_METER_PASSWORD`, а не аргумент командной
  строки (не остаётся в истории оболочки/списке процессов).
- Правило адресации (ТЗ п. 4.3.2): физический адрес для `mode_e` и
  `hdlc_dlms` — последние 5 цифр серийного номера; для `mode_c` —
  серийный номер целиком. Вычисляется автоматически, задавать не нужно.

При ошибке связи (ТЗ Table 2) CLI печатает код ошибки
(`TIMEOUT` / `AUTH_FAILED` / `CONNECTION_LOST` / `CRC_ERROR`) в stderr и
завершается с кодом 1; для `CONNECTION_LOST` дополнительно отмечается,
получена ли часть данных до обрыва (`is_partial`).

## Тесты

```bash
cd gateway
python3 -m pytest -q
```

На момент сдачи Этапа 0: **65 тестов, все зелёные** — юнит-тесты на
кодирование/декодирование каждого протокольного слоя (типы данных
DLMS, HDLC-кадрирование и CRC16/X.25, разбор data readout режима C,
AARQ/AARE, GET.request/response) и интеграционные тесты, поднимающие
эмулятор на localhost и прогоняющие полный цикл чтения для всех 3
профилей — как happy path, так и все 4 сценария ошибок из ТЗ Table 2
(TIMEOUT, AUTH_FAILED без автоповтора, обрыв с флагом `is_partial`,
CRC-ошибка с восстановлением после повтора).

## Инженерные решения, требующие подтверждения на реальном оборудовании

Список мест, где точная спецификация протокола не зафиксирована
дословно в ТЗ/словаре OBIS и была принята инженерная оценка на основе
общего знания стандартов IEC 62056-21 / DLMS-COSEM (Green Book) —
**подлежит сверке до закрытия Этапа 0**:

1. **Формат HDLC-кадра** (`protocols/hdlc.py`) — расположение полей
   Frame Format/HCS/FCS, порядковые номера N(S)/N(R), длина поля адреса
   (в PoC — только однобайтная, до 127; реальные счётчики Risesun могут
   требовать двухбайтную адресацию).
2. **Кодировка AARQ/AARE** (`protocols/dlms.py`) — упрощена относительно
   полного ACSE/BER (нет `sender-acse-requirements`, `mechanism-name`);
   используется OID application-context `{2 16 756 5 8 1 1}` (LN, без
   шифрования) — стандартное значение Green Book, не встречается в
   выгруженном тексте ТЗ дословно.
3. **Теги GET.request/GET.response** (0xC0/0xC4) и коды
   data-access-result — общее знание xDLMS APDU, не из ТЗ.
4. **Option select message режима C/E** (`protocols/mode_c.py`,
   `build_option_select`) — конкретные символы P1/P2/P3 подобраны для
   внутренней согласованности с собственным эмулятором, не сверены с
   реальным поведением счётчика.
5. **Пересчёт полного 6-байтного OBIS в короткий код data readout
   режима C** (`obis6_to_short_code`, поля C.D.E) — правило подобрано
   по образцу ТЗ Table 8, не задокументировано как явное соответствие.
6. **Политика повторов** (`session.py`) — ТЗ описывает повтор на уровне
   транспорта (Table 1) и отдельно повтор запроса при CRC-ошибке
   (Table 2); в PoC обе политики сведены в повтор всей операции
   (подключение + идентификация + чтение) целиком. Для сценариев с
   переиспользуемой сессией (Этапы 2+) это, вероятно, потребует более
   гранулярного повтора отдельных запросов внутри одной сессии.
7. **Auth-сценарий для mode C** — в тексте ТЗ пароль явно фигурирует
   для DLMS-ассоциации (AARQ), но не для текстового readout режима C;
   в PoC сценарий AUTH_FAILED для mode C смоделирован через NAK (0x15)
   в ответ на option select message — версия для демонстрации
   обработки ошибки, не подтверждённый протокол реального счётчика.
8. **DLMS Common-Data-Types** (`protocols/datatypes.py`) — реализовано
   только подмножество тегов, достаточное для целочисленных значений
   регистров; не реализованы дата/время, битовые строки, массивы/
   структуры и масштабирующий множитель атрибута `scaler_unit`
   (класс 3, атрибут 3) — значение в PoC возвращается без применения
   масштаба.
