# ТЗ: нативный установочный пакет MMWS для Windows

Статус: черновик на обсуждение. Ничего из описанного здесь ещё не
реализовано — документ фиксирует архитектуру и открытые решения ДО
начала работы, по решению пользователя написать подробное ТЗ прежде
чем что-либо кодить (2026-09-13).

## 1. Цель и область применения

Сделать так, чтобы весь комплекс MMWS (Backend + Gateway + Frontend +
PostgreSQL) можно было поставить на Windows одним установщиком
(`setup.exe`), БЕЗ Docker и БЕЗ IIS — оба варианта рассмотрены и
отклонены пользователем в этой же сессии:

- Docker Desktop — отклонён, нужен "полностью нативный инсталлятор".
- IIS (ARR/HttpPlatformHandler) — отклонён явно ("лучше тогда вообще
  не использовать IIS").

Итоговая архитектура: Backend сам является веб-сервером (в него
встраивается отдача статики Frontend поверх уже работающего
uvicorn/FastAPI, без отдельного nginx или IIS), Gateway — отдельная
Windows-служба, PostgreSQL — сервис (свой или предустановленный,
см. открытый вопрос §9.1).

## 2. Целевая платформа

- Windows 10/11 x64 и Windows Server 2016+ x64 (одна и та же сборка,
  архитектурных отличий в самом приложении нет).
- 32-битные и ARM-сборки — вне области ТЗ, не запрашивались.

## 3. Как компоненты Docker-архитектуры мапятся на нативную установку

Текущая (`docker-compose.yml`) картина для справки:

| Сервис (Docker)   | Слушает                                                              | Роль |
|-------------------|-----------------------------------------------------------------------|------|
| postgres          | 127.0.0.1:5432                                                        | БД |
| gateway-risesun   | 127.0.0.1:50051 (gRPC, внутренний), 2009 + 2010-2025 (call-home, наружу) | Приём звонков счётчиков, чтение/запись по DLMS |
| backend           | 127.0.0.1:8000                                                        | REST API, воркер задач, планировщик |
| frontend          | 0.0.0.0:5173 → nginx:80 (статика + reverse-proxy /api на backend)     | Веб-интерфейс |

Нативная раскладка:

| Компонент | Как запускается на Windows | Порты |
|---|---|---|
| **MMWS Backend** | Windows-служба `MmwsBackend.exe` (PyInstaller, `uvicorn` встроен в код, не через `python.exe` из системы) — обслуживает и REST API, и статику собранного Frontend (см. §4) | 8000 (или порт из мастера установки) |
| **MMWS Gateway** | Отдельная Windows-служба `MmwsGateway.exe` — call-home листенеры + внутренний gRPC-сервер к Backend | 50051 (только localhost) + 2009, 2010–2025 (наружу, список берётся из текущего `MMWS_EXTRA_CALL_HOME_PORTS`, см. §7) |
| **PostgreSQL** | Служба `postgresql-x64-<версия>` — см. открытый вопрос §9.1 (бандлить инсталлятором или требовать существующий сервер) | 5432 (по умолчанию localhost-only, как и в Docker) |
| **Frontend** | НЕ отдельный процесс — собранный `vite build` (статические файлы) кладутся рядом с Backend и монтируются в FastAPI через `StaticFiles`/`FileResponse` (см. §4.3) | — (отдаётся тем же портом 8000, что и API) |

Из этого следует одно реальное изменение в коде Backend'а (не только
упаковка): нужно добавить раздачу статики Frontend из `main.py` —
сейчас в проде эту роль полностью берёт на себя nginx-контейнер
frontend, для Windows-сборки такого контейнера не будет. Для
Docker/Linux-продакшена ничего не меняется — раздача статики
включается только по флагу/наличию каталога (например,
`MMWS_SERVE_STATIC_DIR`), чтобы не трогать существующее поведение
`docker-compose` вообще.

## 4. Упаковка Python-кода в исполняемые файлы (PyInstaller)

### 4.1. Общий подход

Два отдельных `.spec`-файла — `backend.spec` и `gateway.spec` — каждый
собирает свой `--onedir` бандл (НЕ `--onefile`: `--onefile` распаковывает
себя во временную папку при каждом запуске службы, это плохо сочетается
с автозапуском службы и антивирусами; `--onedir` даёт папку с exe и
DLL/зависимостями рядом, стандартная практика для служб).

### 4.2. Ожидаемые проблемные места (PyInstaller + Windows) — требуют реальной проверки на Windows, не только чтения документации

- **`grpcio`** — частый источник проблем в PyInstaller (нативные `.pyd`,
  собственный небольшой C-runtime); обычно требует явных
  `--collect-all grpc` / `--collect-binaries grpc` в spec-файле.
- **`asyncpg`** — C-расширение с собственным протокольным кодом,
  Windows-wheels существуют, но hidden-imports иногда нужно указывать
  явно (`asyncpg.pgproto`).
- **`psycopg2-binary`** — используется, видимо, синхронно (Alembic
  миграции); binary-wheel уже содержит свою копию `libpq`, отдельно
  ставить PostgreSQL client library не нужно.
- **`bcrypt`/`cryptography`** — нативные расширения, Windows-wheels
  есть, обычно проблем не вызывают, но стоит держать в списке проверки.
- **`uvloop`** — НЕ существует под Windows в принципе (Unix-only). В
  `requirements.txt` он тянется как часть `uvicorn[standard]`, но pip
  на Windows уже сам его не ставит (в uvicorn это опциональная
  зависимость с platform-marker) — то есть на Windows uvicorn и так
  использует штатный `asyncio` event loop. Явных вызовов
  `uvloop.install()` в коде нет (проверено) — переделывать код не
  нужно, это просто нужно знать при объяснении разницы в поведении
  между Linux-продакшеном и Windows-сборкой.
- **Alembic-миграции** (`backend/alembic/versions/*.py`) — при заморозке
  в exe миграции надо явно подключить как `datas=[...]` в spec-файле
  (Alembic ищет их по файловой системе относительно `alembic.ini`, а
  не через обычный Python-импорт) — иначе `alembic upgrade head` внутри
  замороженного exe ничего не найдёт.

### 4.3. Раздача статики Frontend из Backend'а

Изменение в `backend/app/main.py` (см. §3): если задан каталог со
сборкой Frontend (`vite build` → `dist/`), подключить `StaticFiles` на
корень приложения ПОСЛЕ всех API-роутов (иначе перехватит `/api/...`).
`index.html` — SPA-fallback для всех путей фронтенда (аналог
`try_files $uri /index.html` в текущем `nginx.conf`), чтобы прямые
переходы на `/meter-operations/poll` и т.п. не давали 404 при
обновлении страницы.

## 5. Регистрация как служб Windows

Рекомендация: **NSSM** (Non-Sucking Service Manager) — бесплатный,
широко используется для оборачивания произвольных `.exe` в
Windows-службу с автозапуском/автоперезапуском при падении, без
необходимости писать `pywin32`-обвязку (`ServiceFramework`) внутри
самого Backend/Gateway. Минус — NSSM сам по себе не Microsoft-продукт
(хотя очень давно используется индустрией без нареканий) — если для
заказчика принципиален только "чисто майкрософтовский" стек, есть
альтернатива через `pywin32`, но это больше кода на нашей стороне и
больше площадь для ошибок именно в части управления службой (не в
бизнес-логике).

Обе службы:
- Автозапуск при старте Windows (`Automatic`), с задержкой для
  Backend/Gateway после Postgres (NSSM/`sc config` умеет
  `depend on=postgresql-x64-...`).
- Автоперезапуск при падении процесса (Recovery-настройки службы).
- `stdout`/`stderr` перенаправляются в файлы логов (сейчас
  `logging.basicConfig` в `main.py` пишет в stdout — под службой это
  нужно направить в файл; NSSM умеет делать это без изменений в коде,
  через свои настройки `AppStdout`/`AppStderr`).

## 6. Мастер установки (Inno Setup)

Рекомендация: **Inno Setup** (не WiX) — заметно быстрее писать и
отлаживать сценарий, готовый `setup.exe` без MSI-инфраструктуры;
WiX/MSI имеет смысл, только если заказчику нужно централизованное
разворачивание через GPO/SCCM в масштабе многих машин — этого
требования сейчас нет.

Шаги мастера (черновой список, уточнить с пользователем):
1. Лицензионное соглашение / приветствие.
2. Каталог установки (по умолчанию `C:\Program Files\MMWS`).
3. (Если бандлим Postgres, см. §9.1) — тихая установка PostgreSQL,
   либо (если не бандлим) — поля для подключения к уже существующему
   серверу (host/port/user/password/имя БД).
4. Порт Backend (по умолчанию 8000) и диапазон call-home портов для
   Gateway (по умолчанию как в `docker-compose.yml`: 2009, 2010–2025)
   — с возможностью сузить список, если у заказчика не 17 РЭС.
5. Установка файрвол-правил (см. §7) — обязательный шаг, не опция,
   иначе счётчики физически не смогут дозвониться.
6. Копирование файлов, регистрация служб, прогон `alembic upgrade
   head`, запуск `app.bootstrap` (создание супер-администратора — эта
   логика уже есть и не меняется, просто вызывается не из Docker
   CMD, а из шага установки/первого запуска службы).
7. Финальный экран — ссылка на `http://localhost:<порт>` и логин
   супер-администратора по умолчанию.

Удаление (`unins000.exe`): останавливает и удаляет обе службы, удаляет
файрвол-правила; **данные PostgreSQL по умолчанию не трогает** — как
минимум спросить пользователя явно на экране удаления ("удалить и
данные тоже?"), т.к. это необратимая потеря показаний/профилей по
всему парку.

Обновление версии: тот же `setup.exe` определяет, что MMWS уже
установлен (по ключу реестра/файлу версии), останавливает службы,
заменяет бинарники, прогоняет `alembic upgrade head` (миграции уже
устроены так, что накатываются инкрементально — ничего менять не
нужно), запускает службы обратно.

## 7. Файрвол

Инсталлятор обязан добавить правила `Входящее` для:
- TCP 2009 и 2010–2025 (call-home — счётчики звонят на реальный IP
  машины, без доступа снаружи система бесполезна) — `netsh advfirewall
  firewall add rule` или PowerShell `New-NetFirewallRule`.
- TCP 8000 (или выбранный порт Backend) — доступ операторов к
  веб-интерфейсу с других машин в сети предприятия.

50051 (gRPC Backend↔Gateway) — правило НЕ нужно, это чисто
localhost-трафик (как и в Docker, `127.0.0.1:50051:50051`).

## 8. Известные технические риски, требующие проверки НА РЕАЛЬНОЙ Windows (не проверяются на этой Linux-машине)

Часть этого списка уже отмечена выше (§4.2) для PyInstaller-сборки;
отдельно, по существу поведения самой системы под Windows:

1. **Event loop Gateway на Windows** — `asyncio` без `uvloop`
   использует `ProactorEventLoop` (через IOCP) вместо epoll-based
   реализации на Linux. Gateway одновременно держит пул из **до 1000
   соединений** (`DEFAULT_WINDOW_SIZE`, см. `callhome.py`) на 17
   портах — по логике IOCP это должно масштабироваться не хуже, но
   реальной нагрузочной проверки на Windows не было. Рекомендация:
   прогнать хотя бы часть реального парка (или синтетическую нагрузку)
   на Windows-стенде перед вводом в эксплуатацию.
2. **Лимиты файловых дескрипторов/хендлов** — на Linux уже находили
   реальный баг с упором в soft-limit 1024 (см. DECISIONS.md,
   2026-09-10), сейчас выставлено `ulimits.nofile: 65536` в
   docker-compose. У Windows нет прямого аналога `ulimit`, но есть
   собственные лимиты на количество хендлов/сокетов на процесс —
   требует отдельного изучения, если на нагрузке всплывут похожие
   симптомы ("TCP жив, выше тишина").
3. **PyInstaller + `grpcio`/`asyncpg`** — см. §4.2, нужно реально
   собрать и прогнать интеграционные тесты (уже существующие в
   `backend/tests`, `gateway/tests`) против замороженных exe, а не
   только против `python -m pytest` в виртуальном окружении.
4. **Порт 5432 конфликт** — если на машине уже стоит другой Postgres
   (частый случай на серверах предприятия), нужен выбор порта в
   мастере установки, а не жёстко зашитый 5432.

## 9. Открытые вопросы — нужно решение пользователя

### 9.1. PostgreSQL: бандлить в установщик или требовать существующий сервер?

- **Бандлить** (рекомендация, раз речь про "весь комплекс") — тихая
  установка официального инсталлятора PostgreSQL для Windows (EDB)
  как шаг Inno Setup-мастера. Плюс: truly self-contained, ничего не
  нужно ставить руками заранее. Минус: официальный инсталлятор
  PostgreSQL — это несколько сотен МБ внутри нашего setup.exe, плюс
  свои нюансы тихой установки (обязательные параметры командной
  строки, лицензия PostgreSQL — она BSD-подобная, свободна для
  распространения).
- **Требовать внешний Postgres** — инсталлятор просто спрашивает
  строку подключения к уже поднятому серверу (in-house DBA заказчика).
  Легче/меньше наш setup.exe, но не подходит, если у заказчика нет
  своего администратора БД.

### 9.2. Как соберём и проверим итоговый `setup.exe`?

Я не могу собрать и протестировать настоящий Windows-исполняемый файл
из этого Linux-окружения — PyInstaller и Inno Setup должны выполняться
на Windows. Варианты (уже поднимались, ответ пользователя пока не
получен):
- **GitHub Actions, раннер `windows-latest`** — пишу workflow, он на
  реальной Windows в облаке собирает PyInstaller-бандлы и Inno
  Setup-инсталлятор, кладёт готовый `setup.exe` артефактом сборки.
  Плюс: полностью воспроизводимо, не нужен свой Windows. Минус: нужен
  GitHub-репозиторий (сейчас `git remote` не настроен вообще).
- **Windows-машина под рукой** — я готовлю все файлы (spec'ы, .iss,
  инструкцию), сборку и первую проверку пользователь (или коллега)
  делает сам по готовым командам.

### 9.3. Тихая (unattended) установка нужна?

Если планируется разворачивание на несколько машин сразу, имеет смысл
сразу поддержать флаги тихой установки в Inno Setup (`/SILENT`,
предустановленные ответы через `.iss`-параметры), а не только
интерактивный мастер — но это нужно знать заранее, тихая установка
проектируется вместе с обычной, не пристёгивается потом.

### 9.4. Цифровая подпись `setup.exe`?

Без code-signing сертификата Windows SmartScreen будет показывать
предупреждение "Windows защитила ваш компьютер" при первом запуске
незнакомого установщика — не блокирует работу, но выглядит тревожно
для конечного пользователя/заказчика. Нужен сертификат подписи кода
(платный, обычно оформляется на юрлицо) — вне нашего контроля, но
стоит решить заранее, готовы ли идти с неподписанным установщиком на
первое время.

## 10. Что НЕ меняется

- Сам код Backend/Gateway/Frontend по бизнес-логике не переписывается
  — вся текущая функциональность (приоритеты job'ов, событийное
  чтение call-home, суточный сброс очереди и т.д., см. DECISIONS.md)
  переносится как есть. Единственное содержательное изменение в коде —
  раздача статики Frontend из Backend'а для Windows-сборки (§4.3),
  под флагом, не трогающим поведение Docker/Linux-продакшена.
- Docker-развёртывание (`docker-compose.yml`) остаётся основным путём
  для Linux-продакшена — Windows-инсталлятор существует ПАРАЛЛЕЛЬНО,
  не взамен.
