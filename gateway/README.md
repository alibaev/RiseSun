# MMWS Protocol Gateway — PoC Этапа 0

Минимальный CLI-процесс, подтверждающий возможность чтения показаний со
счётчиков Risesun по трём протокольным профилям (ТЗ п. 4.3.2):
IEC 62056-21 режим C, IEC 62056-21 режим E, HDLC + DLMS/COSEM.

Соответствует Этапу 0 согласно `../Promt_MMWS.md` (раздел «Этап 0»): без
gRPC, без базы данных, без пользователей/ролей — только протокольный слой.

## ⚠️ Программные эмуляторы vs реальное оборудование

Пакет `mmws_gateway.emulators` содержит **программные эмуляторы**
счётчика (по одному на каждый протокольный профиль), используемые
интеграционными тестами (`tests/test_integration_*.py`) и локальной
отладкой CLI.

**Обновление 2026-08-18 — проверка на реальном оборудовании начата.**
Профиль HDLC + DLMS/COSEM сверен с реальным трафиком двух настоящих
счётчиков Risesun (pcap-дампы легитимных сеансов легитимного
приложения Risesun Smart Meter Manage) — найдены и исправлены
несколько расхождений с изначальными предположениями PoC (см. раздел
ниже и `../DECISIONS.md`). `tests/test_real_capture_replay.py`
воспроизводит эти реальные байты как регрессионный тест: наш
`encode()` для SNRM/AARQ/GET побайтово совпадает с тем, что шлёт
рабочее приложение, а `decode()` реальных ответов счётчика даёт
корректное показание (666.19 кВт·ч).

**Что ещё не подтверждено:** живое чтение НАПРЯМУЮ через CLI/Gateway
против звонящего домой счётчика пока не удалось — счётчик использует
модель «звонок домой» (счётчик сам инициирует TCP-соединение), не
описанную в ТЗ (там Gateway — инициатор). Есть строительный блок
(`TcpServerTransport`), но полноценная архитектура серверного режима
(листенер, сопоставление соединения со счётчиком по объявленному
адресу, обработка периодических keepalive-кадров) не реализована —
см. `../DECISIONS.md`, раздел «Живые попытки чтения». Профили mode C и
mode E по-прежнему проверены только против собственных эмуляторов.

## Установка

```bash
cd gateway
pip install --user -e .          # прод-зависимости отсутствуют (stdlib)
pip install --user -e '.[test]'  # + pytest для тестов
```

## Использование

```bash
export MMWS_METER_PASSWORD='пароль_доступа'   # не для профиля mode_c
gateway read --profile hdlc_dlms \
    --host 192.168.1.50 --port 4059 \
    --serial 202006003607 \
    --obis 1.1.1.8.0.ff \
    --timeout-ms 5000 --retries 3
```

- `--profile`: `mode_c` | `mode_e` | `hdlc_dlms`.
- `--obis`: 6-байтная hex-нотация `A.B.C.D.E.F` (как в словаре OBIS,
  например `1.1.1.8.0.ff` — суммарная активная энергия приёма). Для
  `mode_c` Gateway автоматически приводит код к короткой десятичной
  нотации data readout (см. `mmws_gateway.protocols.mode_c.obis6_to_short_code`
  и оговорку в отчёте Этапа 0 — соответствие не подтверждено на
  реальном оборудовании).
- `--password`: только для `mode_e`/`hdlc_dlms`. Пароль **никогда** не
  имеет дефолта и не логируется; предпочтительный способ передачи —
  переменная окружения `MMWS_METER_PASSWORD`, а не аргумент командной
  строки (не остаётся в истории оболочки/списке процессов).
- Правило адресации (ТЗ п. 4.3.2): физический адрес для `mode_e` и
  `hdlc_dlms` — последние 5 цифр серийного номера; для `mode_c` —
  серийный номер целиком. Вычисляется автоматически, задавать не нужно.

При ошибке связи (ТЗ Table 2) CLI печатает код ошибки
(`TIMEOUT` / `AUTH_FAILED` / `CONNECTION_LOST` / `CRC_ERROR`) в stderr и
завершается с кодом 1; для `CONNECTION_LOST` дополнительно отмечается,
получена ли часть данных до обрыва (`is_partial`).

На 2026-08-18: **75 тестов, все зелёные** — юнит-тесты на
кодирование/декодирование каждого протокольного слоя (типы данных

## Инженерные решения, требующие подтверждения на реальном оборудовании

### Закрыто проверкой на реальном оборудовании (2026-08-18)

Ранее числившиеся здесь пункты, подтверждённые/исправленные по
реальному трафику двух счётчиков Risesun (полный разбор — см.
`../DECISIONS.md`, тест — `tests/test_real_capture_replay.py`):

- **Формат HDLC-кадра, адресация** — реальные счётчики используют
  4-байтную двухкомпонентную адресацию (`upper=1, lower=физический
  адрес`), не однобайтную с приведением по модулю. Исправлено в
  `protocols/hdlc.py` (`server_hdlc_address`, многобайтный
  encode/decode); `DEFAULT_CLIENT_ADDRESS` исправлен на `0x30`.
- **LLC-заголовок** — информационное поле I-кадра обёрнуто в 3-байтный
  LLC-заголовок (`E6 E6 00`/`E6 E7 00`), которого не было в исходном
  PoC. Добавлено в `protocols/dlms.py` (`wrap_llc_command`/`unwrap_llc`).
- **Кодировка AARQ** — реальный счётчик требует `sender-acse-requirements`
  и `mechanism-name` (OID `{2 16 756 5 8 2 1}`, LLS) и
  `user-information`/InitiateRequest в дополнение к
  `calling-authentication-value`; без них ассоциация не устанавливается.
  Добавлено в `build_aarq`. `parse_aare` переписан на генерический
  разбор TLV (реальный AARE несёт `application-context` перед `result`).
- **SNRM с согласованием HDLC-параметров** — реальный SNRM несёт
  информационное поле (max info length/window size); добавлено как
  `SNRM_PARAMETER_NEGOTIATION`.
- **Теги GET.request/GET.response** (0xC0/0xC4) — подтверждены точно
  как в PoC, отклонений не найдено.
- **DLMS Common-Data-Types** — добавлены `structure`(0x02), `enum`(0x16),
  `long64`/`long64-unsigned` (0x14/0x15): реальный `scaler_unit`
  приходит структурой, значение энергии у одного из счётчиков — int64
  (у второго — int32, оба теперь поддержаны).
- **Вендорская особенность Risesun**: фактическое значение суммарной
  активной энергии читается GET'ом по OBIS `96.80.0` (не по
  стандартному `1.8.0` — тот используется только для чтения
  `scaler_unit`, атрибут 3). Подтверждено словарём `OBIS.xlsx`
  (`Read_Tree_полное_дерево`, `96.80.0` подписан «Total» под веткой
  «Total Active Energy»). Это не протокольная деталь Gateway, а знание
  о конкретной адресации объектов у Risesun — учитывать на уровне
  вызывающего кода (Backend, Этап 1+).

### Всё ещё требует подтверждения

1. **Option select message режима C/E** (`protocols/mode_c.py`,
   `build_option_select`) — конкретные символы P1/P2/P3 подобраны для
   внутренней согласованности с собственным эмулятором, не сверены с
   реальным поведением счётчика (профили mode C/mode E пока не
   проверялись на реальном оборудовании).
2. **Пересчёт полного 6-байтного OBIS в короткий код data readout
   режима C** (`obis6_to_short_code`, поля C.D.E) — правило подобрано
   по образцу ТЗ Table 8, не задокументировано как явное соответствие.
3. **Политика повторов** (`session.py`) — ТЗ описывает повтор на уровне
   транспорта (Table 1) и отдельно повтор запроса при CRC-ошибке
   (Table 2); в PoC обе политики сведены в повтор всей операции
   (подключение + идентификация + чтение) целиком. Для сценариев с
   переиспользуемой сессией (Этапы 2+) это, вероятно, потребует более
   гранулярного повтора отдельных запросов внутри одной сессии.
4. **Auth-сценарий для mode C** — в тексте ТЗ пароль явно фигурирует
   для DLMS-ассоциации (AARQ), но не для текстового readout режима C;
   в PoC сценарий AUTH_FAILED для mode C смоделирован через NAK (0x15)
   в ответ на option select message — версия для демонстрации
   обработки ошибки, не подтверждённый протокол реального счётчика.
5. **Транспортная модель «звонок домой»** — как минимум часть
   счётчиков сама инициирует TCP-соединение к Gateway, а не наоборот
   (расхождение с ТЗ Table 1). `TcpServerTransport` (`transport.py`) —
   только строительный блок; полноценный листенер с сопоставлением
   входящего соединения записи в реестре `meters`, обработкой
   keepalive-кадров и логикой повторных подключений не реализован — см.
   `../DECISIONS.md`.
6. **Точное время между принятием соединения и отправкой SNRM** —
   живой тест против звонящего домой счётчика пока не завершился
   успехом; счётчик в наблюдаемых сессиях не требовал подтверждения на
   свой начальный кадр объявления, но и не отвечал на SNRM,
   отправленный через миллисекунды после этого кадра — требуется ещё
   одна проверка на реальном оборудовании (см. `../DECISIONS.md`).
