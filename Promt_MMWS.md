## 0. Роль и источники истины

Ты выступаешь в роли technical lead на проекте разработки веб-сервиса
**MMWS (Meter Management Web Service)** — замены настольного приложения
Risesun Smart Meter Manage v2.0.1.5 для энергетической инфраструктурной организации.

Проект имеет три обязательных к соблюдению документа — они приложены рядом с этим
промтом, прочитай их целиком перед началом работы:

1. **TZ.docx** — техническое задание, источник
   всех функциональных и нефункциональных требований (версия с учётом

2. **API.docx** — обязательная спецификация
   API-контракта для интеграции с внешней биллинговой системой (раздел 4.2.9,

3. **OBIS.xlsx** — расшифрованный словарь OBIS-кодов,
   форматов кодирования данных и параметров конкретно для счётчиков Risesun

   протокольного слоя вместо того, чтобы искать/угадывать OBIS-коды по общим
   стандартам DLMS — здесь уже подтверждённые значения из реальной базы данных
   производителя.

Если требование в этом промте противоречит ТЗ — приоритет у ТЗ, сообщи о
противоречии, не изобретай компромисс молча.

## 1. Что мы строим (сжато)

Веб-сервис для инженеров/диспетчеров энергокомпании: удалённая настройка,
диагностика и снятие показаний со счётчиков электроэнергии, подключённых по
IP-сети (GPRS/Ethernet), через браузер, с многопользовательским доступом,
ролями, полным аудитом операций записи и интеграцией с внешней биллинговой
системой.

Счётчики говорят по трём протокольным профилям: **IEC 62056-21 режим C**,
**IEC 62056-21 режим E**, **HDLC + DLMS/COSEM**. Это — компонент наивысшего
риска в проекте (см. раздел 3 этого промта).

**Граница текущего проекта (важно):** несмотря на то что архитектура
проектируется как многовендорная (реестр Gateway, роль «Супер-администратор» —
см. ТЗ п. 4.1.1), **весь объём работ в рамках этого промта — только для
счётчиков Risesun.** Не начинай реализацию Gateway-драйверов для других
производителей, даже если архитектура это уже позволяет технически — это
Этап 6, отдельный будущий контракт (ТЗ, п. 1.4). Задача сейчас — довести один
протокольный путь до продакшена, а не распыляться на несколько сразу.

## 2. Технологический стек (зафиксирован, не менять без согласования)

| Компонент | Технология |
|---|---|
| Protocol Gateway | Node.js (TypeScript) либо Python — выбрать один и придерживаться |
| Backend API (AMI/HES Core) | NestJS (TypeScript) либо FastAPI (Python) — должен совпадать по языку с Gateway, чтобы не плодить два рантайма без необходимости |
| Внутренний RPC Backend ↔ Gateway | gRPC (см. ТЗ, п. 4.1) |
| БД | PostgreSQL |
| Очередь фоновых задач | персистентная (Redis + BullMQ, либо Postgres-based, например pg-boss — не in-memory) |
| Frontend | React + TypeScript (SPA) |
| Развёртывание | Docker Compose, on-premise у заказчика (сервер: Ubuntu Server 22.04.5, рабочая директория `~/mmws` — см. документ «Подготовка сервера MMWS») |
| Секреты | Vault / аналог — пароли счётчиков и AES-ключи никогда не в конфиге и не в git; на Этапе 0–1 допустим `.env` с правами 600, не в git |

Если предлагаешь отклониться от стека — обоснуй явно и останови работу до
подтверждения человеком.

## 3. Архитектурные принципы (non-negotiable)

1. **Protocol Gateway строго отделён от Backend API.** Gateway не знает о
   пользователях, ролях, JWT — только протокол, сессии со счётчиками, таймауты,
   повторы. Backend не реализует протокольную логику напрямую — только вызывает
   Gateway по gRPC.
2. **Каждая операция записи параметра на счётчик — audit-first.** Если код пишет
   параметр на счётчик без предварительной проверки, что операция будет
   залогирована в `parameter_write_history`/`audit_log`, это баг, а не
   недоработка "на потом".
3. **Длительные операции — асинхронны.** Чтение профиля нагрузки, пакетное
   отключение/подключение — job с `job_id`/`batch_id`, статусом, докачкой при
   обрыве. Никаких синхронных HTTP-запросов, блокирующих на минуты.
4. **Секреты счётчиков зашифрованы в покое.** Пароль DLMS, AES-ключ канала —
   шифруются перед записью в БД, расшифровываются только на время вызова
   Gateway.
5. **Биллинг-интеграция платформонезависима.** REST/JSON, HTTPS, Bearer-токен,
   без предположений о клиентской платформе (не привязываться к 1С в коде и
   комментариях — см. техрегламент API).
6. **Multi-vendor реестр закладывается архитектурно, но не реализуется сейчас.**
   Таблица `gateways` и привязка `meters.gateway_id` — да, с самого начала
   (ТЗ п. 4.1.1). Драйверы для производителей, кроме Risesun — нет, это вне
   рамок текущего проекта (см. раздел 1 выше).
7. **Регистрация нового Gateway в реестре — только через явное подтверждение
   роли «Супер-администратор».** Даже если сейчас в системе будет
   зарегистрирован только один Gateway (Risesun) — не реализуй авто-регистрацию
   без подтверждения, это требование безопасности, а не заглушка на будущее.
8. **Ничего сверх ТЗ без явного запроса заказчика.** В частности: НЕ добавлять
   мультиязычность интерфейса (вопрос был поднят и отклонён), не добавлять
   функции, которых нет в разделе 4 ТЗ, "чтобы было на будущее".

## 4. Порядок работы — строго поэтапно

Разработка идёт по этапам из раздела 6 ТЗ. **Нельзя начинать этап N+1, пока не
выполнен критерий завершения этапа N.** Ниже — конкретизация первых этапов
для старта.

### Этап 0 — PoC протокольного слоя (делаем прямо сейчас)

Цель: подтвердить, что мы можем прочитать показания с реального (или
эмулированного) счётчика на всех трёх протокольных профилях, **до** того как
писать хоть одну строчку Backend/Frontend кода.

Задачи:

1. Подними минимальный Gateway-процесс с CLI-интерфейсом (без gRPC, без БД) —
   команда вида `gateway read --profile hdlc_dlms --host <ip> --port <port>
   --obis 1.0.1.8.0`.
2. Реализуй транспортный уровень: TCP-подключение, таймаут 5000 мс (дефолт,
   конфигурируемый), до 3 повторов с возрастающей задержкой (ТЗ п. 4.3.1).
3. Реализуй по очереди три протокольных профиля (ТЗ п. 4.3.2):
   - IEC 62056-21 режим C — идентификация `/?!<CR><LF>`, переключение
     baud rate, текстовый обмен;
   - IEC 62056-21 режим E — идентификация + переход на HDLC-кадрирование;
   - HDLC + DLMS/COSEM — HDLC-кадры, AARQ/AARE, GET/SET/ACTION над COSEM-
     объектами по OBIS-кодам.
   Правило адресации: для режима E и HDLC-DLMS физический адрес — последние
   5 цифр серийного номера; для режима C — серийный номер целиком.
4. Если реального счётчика нет под рукой — напиши минимальный TCP-эмулятор
   счётчика для каждого профиля (по документации протокола), чтобы
   гонять интеграционные тесты Gateway против него. Явно пометь в коде и в
   README, что это эмулятор, а не замена реальным полевым испытаниям.
5. Обработка ошибок по таблице ТЗ п. 4.3.4 (TIMEOUT, AUTH_FAILED, обрыв при
   частичном чтении, CRC-ошибка) — реализуй все четыре сценария с тестами.

Definition of Done этапа 0: `gateway read` успешно возвращает показание хотя бы
с одного счётчика/эмулятора каждого из трёх профилей; есть юнит- и
интеграционные тесты на все сценарии ошибок из п. 4.3.4; нет ни одного
секрета в открытом виде в коде/конфиге.

**Не переходи к этапу 1, пока это не выполнено и не подтверждено.**

### Этап 1 — MVP чтения

- Backend API (см. ТЗ п. 4.1, Приложение А) + PostgreSQL (схема — Приложение Б
  ТЗ, минимум таблиц: `meters`, `meter_readings`, `event_log`, `tamper_log`,
  `meter_status_snapshots`, `users`, `audit_log`).
- Аутентификация (логин/пароль → JWT), роли согласно ТЗ п. 4.2.1
  (Оператор / Инженер / Наблюдатель / Администратор / Супер-администратор) —
  реализуй RBAC-мидлварь сразу, не "потом". Роль «Супер-администратор» на
  этом этапе достаточно завести как отдельный уровень прав (таблица `gateways`
  и её API появятся позже, но роль в модели данных должна существовать с
  самого начала, чтобы не было миграции ролевой модели постфактум).
- Gateway оборачивается в gRPC-сервис, Backend вызывает его для операций
  чтения из ТЗ п. 4.2.3.
- Заведи таблицу `gateways` (ТЗ п. 4.1.1, Приложение Б) и зарегистрируй в ней
  единственный на данном этапе экземпляр — Gateway для Risesun — через API
  `/api/gateways` с подтверждением ролью «Супер-администратор» (не через
  прямую вставку в БД в обход API — сама процедура регистрации тоже часть
  функционала, который нужно реализовать и проверить).
- Минимальный Frontend: список счётчиков, карточка счётчика, просмотр
  показаний/журналов. Без функций записи.

### Этап 2 — Запись параметров

- Реализуй операции записи ТЗ п. 4.2.4 (дата/время, режимы отображения,
  тарифное расписание, параметры профиля нагрузки, параметры GPRS).
- Каждая операция — через `parameter_write_history` с полями: пользователь,
  время, счётчик, параметр, старое/новое значение, результат.
- UI: явное подтверждение перед отправкой команды записи.

### Этап 3 — Профиль нагрузки

- Асинхронное чтение (ТЗ п. 4.2.3), докачка при обрыве, флаг `is_partial`.
- WebSocket или polling для прогресса на Frontend.

### Этап 4 — Автоматизация

- `scheduled_jobs` (cron-подобные расписания), массовое применение схем
  параметров (`parameter_schemes`), уведомления (offline-счётчик,
  tamper-событие, ошибка задачи).

### Этап 5 — Биллинг-интеграция и завершающая доработка

- Реализуй сегмент `/api/v1/billing/*` **строго по техрегламенту API**:
  `GET /readings`, `GET /tariffs`, `POST /disconnect-batch`,
  `POST /reconnect-batch`, `GET /disconnect-batch/{batch_id}`.
- Обязательно: отдельная аутентификация (API-ключ, Bearer), `Idempotency-Key`
  на пакетных операциях, rate limiting (60 req/min на ключ — дефолт из
  регламента), пагинация, единый формат ошибок (`error.code`, `error.message`,
  `error.request_id`).
- Disconnect Control через DLMS class 70 (HDLC-DLMS профиль); для IEC 62056-21
  — проверить поддержку на этапе PoC (может быть недоступно на части моделей).
- Мониторинг, экспорт, финальное тестирование по критериям ТЗ раздела 7.

## 5. Гварды (проверяй сам, не жди ревью)

Перед тем как считать любую задачу выполненной, проверь:

- [ ] Секрет (пароль счётчика, AES-ключ, API-ключ) нигде не лежит в открытом
      виде — ни в коде, ни в `.env` в репозитории, ни в логах.
- [ ] Операция записи параметра на счётчик не проходит без записи в аудит.
- [ ] Длительная операция (профиль нагрузки, пакетное отключение) не
      реализована как синхронный блокирующий вызов.
- [ ] Protocol Gateway не содержит импортов/зависимостей от слоя
      пользователей/ролей/HTTP-сессий.
- [ ] Ошибки протокола (таймаут, auth failed, обрыв, CRC) не проглатываются
      молча — они долетают до статуса задачи с понятной причиной.
- [ ] Новый функционал явно есть в ТЗ. Если ты хочешь добавить что-то "для
      полноты" — сначала спроси, не добавляй.
- [ ] Пароли **пользователей системы** хешируются (bcrypt или аналог по
      стойкости) — это отдельно от шифрования секретов счётчиков (принцип 4
      раздела 3), не подменяет его (ТЗ п. 4.5).
- [ ] Соединения веб-интерфейс ↔ Backend API, включая WebSocket — по TLS
      (ТЗ п. 4.5).
- [ ] Изменяющие состояние запросы веб-интерфейса защищены от CSRF, вывод
      экранирован от XSS (ТЗ п. 4.5).
- [ ] Backend API остаётся stateless и допускает горизонтальное
      масштабирование; Protocol Gateway допускает развёртывание нескольких
      экземпляров (ТЗ п. 4.6).
- [ ] Постановка операции в очередь (ответ веб-интерфейсу до фактического
      опроса счётчика) укладывается в целевые 500 мс для 95% запросов
      (ТЗ п. 4.7).

## 6. Формат работы с агентом

- Каждый этап — отдельная ветка, отдельный PR, отдельное ревью человеком
  перед началом следующего этапа.
- Протокольный слой (этап 0 и любые доработки Gateway) — обязательно с
  тестами против эмулятора или реального оборудования; PR без тестов на
  протокольные сценарии ошибок не принимается.
- При неопределённости в требовании — свериться с ТЗ и техрегламентом API
  первым делом; если там нет ответа — задать один точный вопрос человеку,
  не гадать и не расширять скоуп по умолчанию.
- Комментарии в коде и README — на русском языке (ТЗ п. 4.4.4: лингвистическое
  обеспечение системы — русский язык; это же касается пользовательской
  документации и разумно распространить на код проекта для консистентности
  с командой заказчика).

## Быстрый чек-лист для первого запуска агента

1. Прочитать ТЗ, техрегламент API и словарь OBIS-кодов целиком.
2. Подтвердить выбор языка стека (Node.js/TS или Python) — если не указано

3. Проверить окружение сервера (см. документ «Подготовка сервера MMWS»):
   Docker/Docker Compose установлены, `.env` создан с правами 600 и не в
   git, рабочая директория `~/mmws`.
4. Начать с этапа 0 (протокольный PoC), ничего другого не трогать, пока
   Definition of Done этапа 0 не выполнен. Помнить про границу проекта
   (раздел 1) — только Risesun, никаких других производителей в этом
   контракте.
